## 0. Executive summary (what matters for Metallium)

1. **Layering (Verified).** Three layers. `api/*` is the public model (GpuDevice, CommandEncoder, RenderPass, RenderPipeline, GpuBuffer/Texture, GpuFormat). `frontend/*` (FrontendGpuDevice, FrontendCommandEncoder, FrontendRenderPass, FrontendGpuSurface, PipelineBuilder, GlslCompiler) does validation, GLSL->SPIR-V, reflection and binding rewrite. `backend/api/*` is the 5-interface SPI a backend implements: `GpuDeviceBackend`, `CommandEncoderBackend`, `RenderPassBackend`, `GpuSurfaceBackend`, `BackendRenderPipeline` (+ `SpvModule`). `GpuBackend` (loadLibrary/createWindow/createDevice) is the bootstrap, and `createDevice` returns `new FrontendGpuDevice(<your GpuDeviceBackend>)`. GlBackend and VulkanBackend both do exactly this.
2. **No official registration point (Verified).** `PreferredGraphicsApi.getBackendsToTry()` hard-codes `new GlBackend()` / `new VulkanBackend()` (`mc26.3/net/minecraft/client/PreferredGraphicsApi.java:L32-36`). A mod needs a mixin on that method (or on the Minecraft ctor loop). Metallum already does this (downstream: `metallum/src/main/java/com/metallum/mixin/PreferredGraphicsApiMixin.java`, `@Inject HEAD cancellable` on `getBackendsToTry`). `PreferredGraphicsApi` is a closed enum (DEFAULT/OPENGL/VULKAN) that feeds `Options.preferredGraphicsBackend` (Codec, cycle button), so adding a METAL constant needs enum-extension tooling; unverified whether anything in the Fabric stack offers it.
3. **A Metal backend receives SPIR-V, not GLSL (Verified).** The frontend compiles vanilla `#version 330` GLSL with shaderc (target Vulkan 1.2 env, auto-bind uniforms, optimization level 0) and reflects with SPIRV-Cross (spvc). Descriptors are rewritten to set 0 / binding = dense uniform index. The backend gets `SpvModule.spv()` (ByteBuffer of SPIR-V words), entry point always `"main"`, plus a reflection API. **Even the OpenGL backend consumes SPIR-V**: it runs SPIRV-Cross SPIR-V->GLSL 330 (`GlPipelineRecompiler`). Vanilla therefore already ships and loads shaderc and spvc natives (lwjgl-shaderc/lwjgl-spvc 3.4.3, natives-macos and macos-arm64 are in the 26.3 manifest). A Metal backend is intended to do SPIR-V -> MSL via spvc (the same pattern as GL). Unverified: that the LWJGL spvc build has the MSL backend. Metallum (downstream) has a `MetalCrossShaderCompiler`, which suggests yes.
4. **Uniform model is blocks-only (Verified).** Allowed resources: std140 UBOs, combined image samplers (2D and Cube; 1D/3D/array rejected), texel buffers (`samplerBuffer`/`isamplerBuffer`), one push-constant block (<=128 B, never used by vanilla). Loose non-opaque uniforms are impossible because glslang targets Vulkan semantics. No SSBOs, storage images, compute, geometry/tess, stencil, MSAA, 3D/array textures, compare samplers, mip generation.
5. **Conventions to reproduce** (these decide the visuals):
   - Depth is reverse-Z, zero-to-one. Clear depth = 0.0, default test `GREATER_THAN_OR_EQUAL`, `Projection` swaps near/far and passes `zZeroToOne=true` when `DeviceInfo.isZZeroToOne()`.
   - Vulkan backend does NOT flip the viewport. Intermediate render targets therefore have row 0 == clip y=-1 (identical to GL), `frontFace=CLOCKWISE` compensates for winding, and only the final swapchain blit flips Y. A Metal backend has to reproduce "row 0 == clip y=-1" (likely via vertex-Y flip) or every post pass and scissor will be upside down.
6. **Terrain path (Verified).** Default is `drawIndexedIndirect` multi-draw with an instanced per-section vertex stream (binding 1, step rate 1, `firstInstance` indexes the section) gated on `maxDrawIndirectDrawCount>0 && nonZeroFirstInstance && !multiDrawIndirectHasKnownIssues`. Fallback: per-section `drawIndexed` with a rebound `ChunkSection` UBO (`drawMultipleIndexed`). Metal has no multi-draw-indirect; a backend can either loop (DeviceLimits.maxDrawIndirectDrawCount=1, so the frontend/LevelRenderer already chunk to 1 per call) or use ICBs. Setting `hintsAndWorkarounds.multiDrawIndirectHasKnownIssues=true` forces the simple `drawIndexed` path.
7. **OIT is real and heavy (Verified).** Option `improvedTransparency` (default false) switches `LevelRenderer` from `executeClassicTransparency` to `executeOit` (3 stages DEPTH_BOUNDS / TRANSMITTANCE / ACCUMULATE + composite) using 8-coefficient wavelet transmittance in 2x RGBA16F MRT, an RGBA32F depth-bounds target with MAX blend, `gl_FragDepth` writes, and `texelFetch` on depth-bound targets. Needs 3 simultaneous color attachments in a pass (2 transmittance + none other) and MAX blending.
8. **Raw GL outside backend/opengl: effectively none (Verified within decompiled scope).** Only `NativeLibrariesBootstrap` touches `org.lwjgl.opengl.GL` (library load) and `FrontendRenderPass` imports `VkDrawIndexedIndirectCommand/VkDrawIndirectCommand` for `SIZEOF`. So the game is backend-neutral at the Java level, which is why Sodium/Iris (which use raw GL) are the hard part, not vanilla.
9. **Vulkan on macOS is explicitly attempted** (portability enumeration only on OSX, MoltenVK workarounds), but **GL is tried first on every platform** (DEFAULT = [GL, Vulkan]); Vulkan is not the default anywhere. See section 6.

### 1.1 Package map (Verified)

Semantics that are easy to get wrong:
- **All of these are recorded, GPU-timeline commands.** VK `writeToBuffer` = `transientMemory.uploadStaging(data)` (CPU copy happens immediately) + `vkCmdCopyBuffer` + a global memory barrier (`VulkanCommandEncoder.java:L590-619`); GL does `bufferSubData` immediately (`GlCommandEncoder.java:L274-278`). Callers rely on "ordered w.r.t. later draws". The data must be snapshotted at call time (ByteBuffer is reused by callers).
- **Ordering/hazards:** Vulkan inserts a full `VkMemoryBarrier2` (ALL_COMMANDS/ MEMORY_READ|WRITE, constants `srcStage=65536` etc.) after every render pass end, clear, write, copy (`VulkanCommandEncoder.java:L253-263`, called in `submitRenderPass`, `clear*`, `writeTo*`, `copy*`). All images stay in `VK_IMAGE_LAYOUT_GENERAL` (imageLayout 1 in `L330`, `VulkanRenderPass pushDescriptors imageLayout(1)`). There is **no barrier/resource-state API anywhere**; the contract is "commands execute as if serially, with full visibility between them". Metal must either use hazard-tracked resources (default for non-heap resources) or emit its own fences/barriers between encoders. This is the single biggest semantic duty of a Metal backend.
- **Render pass vs. non-pass commands:** frontend forbids any non-pass command or second pass while a pass is open (`FrontendCommandEncoder.java:L101-103, L236ff`). So the backend sees strictly alternating "blit-ish op" / "render pass" sections. Perfect fit for Metal encoder switching (blit encoder vs render encoder); no compute encoder exists.
- `copyTextureToBuffer(..., Runnable callback, ...)`: callback must run on the render thread *after the GPU has finished the copy*. VK queues it in the 2-deep destruction queue so it fires two `submit()`s later (`VulkanCommandEncoder.java:L798`); GL uses `RenderSystem.queueFencedTask(callback)` (`GlCommandEncoder.java:L396`). Metal: `addCompletedHandler` -> enqueue to render thread. Used for screenshots/readbacks.
- `createFence()`: fence = "everything submitted up to and including the current `submit()` index". `awaitCompletion(timeoutNS)` on the *current* (unsubmitted) index throws unless timeout==0 (then returns false) (`VulkanCommandEncoder.java:L895-935`, `GlCommandEncoder.awaitSubmit L89-112`). `GpuFence.NO_TIMEOUT=-1`.
- Frontend checks done before calling the backend are listed in 1.6.

- The backend is NOT told the pass attachments again after `createRenderPass`; the viewport is implicitly `(0,0,attachW,attachH,0..1)` and scissor = `renderArea` (`VulkanRenderPass.java:L78-91`). `RenderArea` may be a sub-rect (used by region clears).
- Uniforms are replayed: when `setPipeline` is called the frontend re-pushes every stored uniform to the backend (`FrontendRenderPass.java:L105-130`: `this.uniforms.forEach(this::setUniform)`), then `constantsPushed=false`. `setUniform(index, ...)` index is the dense binding index of that pipeline's `CreateInfo.uniforms()`; uniforms the shader doesn't use are filtered out by the frontend (`uniformIndices.getOrDefault(name,-1)`). The backend must be lazy-bind: Vulkan marks `anyDescriptorDirty` and pushes descriptors just before each draw (`VulkanRenderPass.java:L231, pushDescriptors L330-380`).
- UBO offsets must be multiples of `limits.minUniformOffsetAlignment` (frontend throws otherwise, `FrontendRenderPass.java:L151-160`). Texel buffers must be the **entire** buffer (checked only under STRICT_VALIDATION).
- Which draw calls vanilla actually issues (Verified by grep): `draw(3,1,0,0)` fullscreen triangles, `drawIndexed` (via `drawMultipleIndexed`), `drawIndexedIndirect` (terrain). Never used by vanilla: `multiDraw*`, `multiDrawIndexed*`, `drawIndirect`, `pushConstants`, `setBlendConstant` (does not exist). Mods may call them though, so features flags matter.
- The frontend's `drawMultipleIndexed` (`FrontendRenderPass.java:L299-371`) is *not* a backend method: it loops `setVertexBuffer(slot, ...)`, `setIndexBuffer` (only when changed), per-draw `uniformUploader` (`setUniform("ChunkSection", ...)`) and then `backend.drawIndexed(count,1,firstIndex,baseVertex,0)`. So the backend must handle many tiny drawIndexed calls with UBO rebinding at different offsets.

### 1.6 What FrontendGpuDevice/Encoder/RenderPass do before calling the backend
`FrontendGpuDevice` (`RP/frontend/FrontendGpuDevice.java`): owns `FrontendCommandEncoder` (L51), `PipelineBuilder` (L52), optional `TracyGpuProfiler` (if `TracyClient.isAvailable`). Validations: anisotropy range, texture arg checks (above), view range, buffer size. `STRICT_VALIDATION = SharedConstants.IS_RUNNING_IN_IDE` (L36): **the heavy draw-time validation is OFF in production** (`FrontendRenderPass.validateDraw L449+` only checks "no pipeline bound" unconditionally; vertex buffer presence, index buffer usage flags, missing uniforms, closed resources, push-constant presence, depth requirement are all STRICT-only). A Metal backend must therefore be defensive itself against: missing uniforms (null in uniform table), closed resources, missing depth attachment when pipeline wants depth.

`FrontendCommandEncoder` (`RP/frontend/FrontendCommandEncoder.java`): `createRenderPass` (L101-221) checks: no open pass, `colorAttachments.size() <= limits.maxColorAttachments`, at least one attachment, render area inside attachment, each attachment: open, `USAGE_RENDER_ATTACHMENT`, `depthOrLayers==1`, size equal to first attachment. **Null entries allowed in `colorAttachments`** (unused MRT slots, `withUnusedColorAttachment()`); pipelines may have null `ColorTargetState` for those slots. Copy/clear/write ops check usage flags (COPY_DST/COPY_SRC/RENDER_ATTACHMENT; note clears require BOTH RENDER_ATTACHMENT and COPY_DST, `verifyColorTexture L741`). `copyTextureToBuffer` rejects multi-layer sources.

`FrontendRenderPass.setPipeline` (L105-130): requires colorTargetStates.size()==attachments.size() and format equality per non-null attachment. => **backend can build one MTLRenderPipelineState per (pipeline, hasDepth)**; pixel formats are fully determined by the pipeline's ColorTargetStates + (hasDepth ? D32_FLOAT). Vulkan literally compiles two pipelines: `withDepthPipeline` (`depthAttachmentFormat(126)=VK_FORMAT_D32_SFLOAT`, `VulkanRenderPipeline.java:L321`) and, only if `depthStencilState==null`, a `withoutDepthPipeline` (L353). The depth format is hard-wired to D32_FLOAT in the Vulkan backend even though `GpuFormat` has other depth formats.

`FrontendGpuSurface` (`RP/frontend/FrontendGpuSurface.java`): state machine configure -> acquire -> blit (exactly once, requires `USAGE_COPY_SRC`, single-layer color) -> present. Cannot configure/close while acquired.

### 1.7 `TransientMemory` (public API implemented by every encoder backend) `RP/api/buffers/TransientMemory.java:L1-86`
Per-frame (per-`submit()`) bump allocation with four flavors: `allocateCpu` (plain malloc'd ByteBuffer, <=16 B alignment), `allocateStaging` (host-visible, returns `MappedView`), `allocateGpu` (device-local slice, no CPU access) and `allocateGpuMapped` (CPU-writable view that is copied to a device-local slice at close/`recordGpuMappedCopy`), plus `uploadStaging/uploadGpu/multiUpload*` helpers. Each takes `(size, alignment, usage, minimumAllocation, elementSize)` where `minimumAllocation/elementSize` let the allocator return a *shorter* slice than requested (partial fulfillment rounded to elementSize) when the block tail is too small (`TransientBlockAllocator.allocate L108-150`). Lifetime = until the end of the frame's GPU completion (VK rotates after the submit N-2 semaphore). Reusable pieces: `TransientBlockAllocator` (512 KiB blocks, `VulkanTransientMemory.BLOCK_SIZE=524288`, `L34`) and `CpuBlock.memalloc()`. On Apple Silicon (UMA) staging==gpu-mapped==shared MTLBuffer, so a Metal implementation is much simpler than VK's (VK picks heaps by `memoryProperties`, `VulkanTransientMemory.java:L60-130`).
`DynamicUniforms`, `StagedVertexBuffer`, `SpriteContents`, `CubeMapTexture` call this (grep `transientMemory()`).

### 1.8 `DeviceInfo` / `DeviceLimits` / `DeviceFeatures` / `HintsAndWorkarounds` (the capability contract) (Verified)
`DeviceInfo(name, vendorName, driverInfo, isZZeroToOne, backendName, timestampPeriod, limits, features, Set<String> underlyingExtensions, hints, DeviceType)`.
- `isZZeroToOne` drives (a) CPU projection matrices (`Projection.java:L66-73`), (b) shader macro `RENDERPEARL_DEPTH_IS_ZERO_TO_ONE` (`GlslCompiler.java:L81-83`). GL sets it = `GL_ARB_clip_control` present (`GlHeuristics.java:L92`, and calls `glClipControl(LOWER_LEFT, ZERO_TO_ONE)` L150); VK = true. **Metal = true.**
- `DeviceLimits(maxAnisotropy, minUniformOffsetAlignment, maxTextureSize, maxMemoryAllocationSize, maxMultiDrawDirectInterleavedDrawCount, maxColorAttachments, maxDrawIndirectDrawCount)`. `maxTextureSizeForFormat` used for window max size. `maxColorAttachments` must be >= the 2 OIT targets + ... (OIT transmittance pass has `OIT_TRANSMITTANCE_TARGET_COUNT=2` attachments; depth-bounds pass 1) and Registered pipelines use up to `ColorTargetState.MAX_COLOR_TARGETS=8` (`ColorTargetState.java:L21`). Metal supports 8.
- `DeviceFeatures(wireframeFillMode, shaderDrawParameters, multiDrawDirectInterleaved, multiDrawDirectSeparate, multiDrawIndirect, drawIndirect, nonZeroFirstInstance, persistentMapping)`. VK: `(WIREFRAME optional, true, MULTI_DRAW ext, false, true, true, true, true)` (`VulkanDevice.java:L107-116`). GL: `(true, ARB_shader_draw_parameters, false, true, ARB_multi_draw_indirect, ARB_draw_indirect, ARB_base_instance, ARB_buffer_storage)` (`GlHeuristics.java:L104-113`). Consumers: `wireframeFillMode` -> `RenderSystem.supportsWireframe` + `PipelineBuilder` rejects WIREFRAME pipelines when false (`PipelineBuilder.java:L377-381`; they're "optional" pipelines); `shaderDrawParameters` -> macro `RENDERPEARL_INSTANCE_INDEX_INCLUDES_BASE_INSTANCE`; `nonZeroFirstInstance` -> terrain MDI gate; `persistentMapping` + `writeToBufferIsSlow` -> `StagingBuffer.PersistentlyMapped` vs `Cpu` (`StagingBuffer.java:L17-19`).
- `HintsAndWorkarounds(writeToBufferIsSlow, anisotropyHasKnownIssues, isExplicitDepthRequired, multiDrawIndirectHasKnownIssues)`. `isExplicitDepthRequired = Util.isAppleSiliconMac(deviceName)` on BOTH GL and VK (`GlHeuristics.java:L116`, `VulkanDevice.java:L118`) -> macro `RENDERPEARL_EXPLICIT_DEPTH_INVARIANCE` -> OIT shaders write `gl_FragDepth = gl_FragCoord.z` (jar:`include/oit_sample.glsl:L101-103`, `include/oit_add_transmittance.glsl:L46-48`). Vanilla is already working around Apple GPU depth invariance; a Metal backend on Apple Silicon should set this true.
- GL vs VK `DeviceType` guessed by heuristics; irrelevant.

### 1.9 Frame/submit model (Verified, VK as the reference)
- One global command encoder, one `submit()` per frame (called from `Minecraft.renderFrame` after the swapchain blit, `Minecraft.java:L1469`, then `surface.present()` L1472). In `renderFrame`: configure surface if needed -> `acquireNextTexture` (SurfaceException => `surfaceIsInvalid` + re-configure next frame, `L1355-1380`) -> game render -> `blitFromTexture(mainRenderTarget color)` -> `submit()` -> `present()`.
- Frames in flight = 2. VK: `MAX_SUBMITS_IN_FLIGHT=2` (`VulkanCommandEncoder.java:L50`), timeline semaphore, `submit()` ends cmd buffers, signals semaphore, begins next submission, then **blocks up to 5 s for submit index-2** (`L265-285`; timeout => IllegalStateException with checkpoint dump). GL does the same with `glFenceSync` slots (`GlCommandEncoder.submit L79-87`). 2 command pools alternate (`commandPools[2]`, `L59`).
- Destruction queue: `DestructionQueue<Destroyable>(2, ...)` (`DestructionQueue.java`): `close()` of a buffer/texture/sampler/pipeline only enqueues; real destroy happens when the queue rotates (after the next-next submit). Also used for `copyTextureToBuffer` callbacks. => **Closing a resource while the GPU still uses it is legal in the API contract**; the backend must keep it alive 2 submits (Metal: retain until completion handler).
- Texel-buffer views are created per descriptor push and queued for destruction (VK `VulkanRenderPass.java:L345-360`). In Metal the equivalent is `MTLBuffer.makeTexture(descriptor:offset:bytesPerRow:)` - consider caching by (buffer,offset,length,format).
- VMA usage (VK): every buffer is `vmaCreateBuffer` with `VMA_MEMORY_USAGE_AUTO` (usage 8? `allocCreateInfo.usage(8)` = VMA_MEMORY_USAGE_AUTO), host-visible+coherent required when `MAP_READ|MAP_WRITE` (usage bits 3) with `HOST_ACCESS_SEQUENTIAL_WRITE`(1024) for write-only and `HOST_ACCESS_RANDOM`(2048) for read, `AUTO_PREFER_HOST` when `CLIENT_STORAGE|MAP_READ` (bits 5 -> `usage(9)`) (`VulkanGpuBuffer.java:L36-68`). Mapping is ref-counted `vmaMapMemory`; closing a mapped buffer throws (`L113-116`).

## 2. GpuBackend selection, fallback, registration, device loss

- `PreferredGraphicsApi { DEFAULT("default"), OPENGL("opengl"), VULKAN("vulkan") }`, `getBackendsToTry()` = `this==VULKAN ? [vulkan, gl] : [gl, vulkan]` (`PreferredGraphicsApi.java:L32-36`). **DEFAULT and OPENGL both try GL first then Vulkan.** Vulkan is never first unless the user (or `--` launch arg) chose it. No platform branching in these classes => Vulkan is not the default on any platform (Verified).

- **Registration for mods: none official.** Only mixins: inject/override `PreferredGraphicsApi.getBackendsToTry` (public instance method of an enum, easy `@Inject(at=HEAD, cancellable)`; Metallum does it and also overrides `caption()` to rename the DEFAULT button) or wrap the `getBackendsToTry()` call at `Minecraft.java:L508`. - `GpuDeviceLossException`: defined (`RuntimeException(String)`), **only thrown by VulkanUtils** (`VulkanUtils.java:L93`, on VK_ERROR_DEVICE_LOST with checkpoint dump) and **never caught specifically** anywhere in the decompiled scope (grep: no catch sites). There is no device-recreation path; device loss == crash. `GpuOutOfMemoryException` is caught only in `MainTarget.allocate*` (retry with a smaller size, `MainTarget.java:L60-90`) and is thrown by GL's texture/buffer creation. `SurfaceException` is handled as above.
- `GpuBackend.createDevice` of both shipped backends returns `new FrontendGpuDevice(...)` (`GlBackend.java:L66-69`, `VulkanBackend.java:L208`). Using the frontend is effectively mandatory.
- Mod evidence (downstream): nvidium has mixin accessors on `FrontendCommandEncoder`, `FrontendRenderPass`, `GlCommandEncoder`, `GlDevice`; sodium-extra mixes `GlSurface`. These are GL-specific mixin targets that stop working when the Metal backend is active.

## 3. Shader pipeline (frontend/shaders)

### 3.1 Flow (Verified): GLSL -> shaderc -> SPIR-V -> (reflect+rewrite) -> backend
1. `ShaderManager.loadConfigs` reads every resource under `shaders/` (`*.vsh`, `*.fsh`, `shaders/include/*.glsl`) and `post_effect/*.json` from the resource manager (`ShaderManager.java:L98-125`) => **fully resource-pack overridable GLSL** (including `core/*`).
2. `RenderSystem`/`ShaderManager` compile every registered `RenderPipeline` via `device.compilePipeline(pipeline, shaderSource, executor)` (`ShaderManager.java:L71-95`, `PipelineCache.get` L33 compiles missing pipelines synchronously via `.join()` for ad-hoc/post pipelines).
3. `PipelineBuilder.generateBackendCreateInfo` (`PipelineBuilder.java:L65-367`): for each stage `GlslCompiler.compileToSpv(name, source, type, pipeline.getShaderDefines(), shaderSource)`.
4. `GlslCompiler` (`GlslCompiler.java:L74-94, L96-180`): `shaderc_compile_into_spv`, stage only VERTEX(0)/FRAGMENT(1), entry `"main"`, source passed as-is (no preprocessing in Java except shaderc itself), include callback `shaderSource.getInclude(Identifier)` for `#include <minecraft:foo.glsl>` (identifier syntax, `GlslCompiler.java:L37-52`), options: target env `(vulkan=0, version=4202496=Vulkan1.2)`, `auto_bind_uniforms(true)`, `preserve_bindings(false)`, debug info on, **optimization level 0** (so no shaderc optimization; the MSL compiler does the work).
5. **Defines injected** (all as shaderc macro definitions, not `#define` text): `RENDERPEARL_DEPTH_IS_ZERO_TO_ONE` (if `isZZeroToOne`), `RENDERPEARL_EXPLICIT_DEPTH_INVARIANCE` (if hint), `RENDERPEARL_INSTANCE_INDEX_INCLUDES_BASE_INSTANCE` (if `features.shaderDrawParameters`), then every `ShaderDefines.values()` (key=value, e.g. `ALPHA_CUTOUT=0.5`, `OIT_COEFF_COUNT=8`) and every flag (e.g. `MULTIDRAW_TERRAIN`, `OIT_ACCUMULATE`, `OIT`). **No `VULKAN`/`OPENGL`/`METAL` define exists.** (grep of all 72 vanilla shader files: no backend checks except the three RENDERPEARL_ macros.)
6. Vanilla shaders are `#version 330` + `#extension GL_ARB_separate_shader_objects : require`, use `layout(location=N)` in/out, `gl_VertexIndex` (Vulkan-style, e.g. jar:`core/screenquad.vsh`), `layout(std140) uniform Block {}`, `uniform sampler2D X;`, `uniform isamplerBuffer CloudFaces;`. (Verified: 72/72 files are `#version 330`.)
7. `SPIRVModule.reflect()` (spvc, parse SPIR-V -> compiler backend id 0 = NONE `spvc_context_create_compiler(ctx, 0, ir, 0, ...)`, `SPIRVModule.java:L68-160`): lists stage inputs (resource type 3), outputs (4), descriptors for types {1 UNIFORM_BUFFER, 2 STORAGE_BUFFER, 6 STORAGE_IMAGE, 7 SAMPLED_IMAGE, 10 SEPARATE_IMAGE, 11 SEPARATE_SAMPLERS} (`SpvUtil.DESCRIPTOR_TYPES L11`) and push constants (type 9, size via declared struct size). Locations/sets/bindings are read via binary-offset-for-decoration so they can be rewritten in place.
8. Checks and rewrites in `PipelineBuilder`:
   - Vertex inputs matched to `VertexFormat` elements **by name** (`element.name()` == GLSL variable name, e.g. `Position`, `UV2`), `location` taken from the shader; multi-column attributes get consecutive locations (L98-122). Every vertex input must have a matching element (else ShaderCompileException). `Component` decoration (31) forbidden. Base type must match format class: float for UNORM/SNORM/FLOAT, uint for UINT, int for SINT (L147-154) => e.g. `UV2` RG16_SINT must be `ivec2`; vector size <= component count (L170-180).
   - VS->FS interface: each FS input location must have a VS output with equal base type, vector length, flat-ness (L205-260); 64-bit/double/struct interface vars rejected.
   - Descriptors: every shader descriptor name must exist in the RenderPipeline's `BindGroupLayout`s; global dense binding = `uniformBindings.computeIfAbsent(name, size)` in order of first appearance across shaders; `descriptor.binding(newBinding)`, `descriptorSetIndex(0)` (L285-301). Type consistency across stages enforced, plus declared UniformType vs actual (L305-335: image dim 1(2D)/3(Cube)/4(Rect) => COMBINED_IMAGE_SAMPLER, dim 5(Buffer) => TEXEL_BUFFER, 0(1D)/2(3D) rejected).
   - Push constants: <=1 block per shader and size <= pipeline's declared (<=128) (L338-352).
9. Backend receives `CreateInfo` (1.11). `uniforms` = only those used by some shader, in binding order.

### 3.2 Answers
- **Does GL get GLSL and Vulkan SPIR-V?** Both get the same SPIR-V. GL converts SPIR-V->GLSL 330 with spvc (`GlPipelineRecompiler.decompileShader L46-120`: compiler backend `1` = GLSL, options `GLSL_VERSION=330`, `ENABLE_420PACK_EXTENSION=false`, `GLSL_SUPPORT_NONZERO_BASE_INSTANCE=drawParametersSupported`, renames descriptors to `_uniform_%02d_%02d`, interface vars to `_interface_variable_%02d`, push constants -> UBO block `_push_constants`, entry point 0/4 = vertex/fragment). The option IDs are raw ints (33554440 etc.); I decoded GLSL_VERSION and SUPPORT_NONZERO_BASE_INSTANCE from the spvc header numbering (Hypothesis on the rest).
- **What a Metal backend gets:** `SpvModule.spv()` per stage (Vulkan-1.2-environment SPIR-V, descriptor set 0 / dense bindings, entry "main", std140 UBOs, combined image samplers as `OpTypeSampledImage`) + `reflect()` + `CreateInfo` render state. It must (a) run spvc with `SPVC_BACKEND_MSL` (backend id 3 in `spvc_backend`: NONE=0, GLSL=1, HLSL=2, MSL=3 - Inferred from header), (b) assign Metal argument indices for UBO/texture/sampler per binding (spvc MSL resource-binding API, `spvc_compiler_msl_add_resource_binding`), (c) remap vertex attributes to `[[attribute(location)]]` + vertex descriptor from `attribBindings`/`vertexBuffers`, (d) handle combined image samplers (SPIRV-Cross MSL splits them into texture+sampler, needs the same binding for both or a combined-sampler remap), (e) texel buffers -> `texture_buffer<>` / `isamplerBuffer` -> `texture2d`-backed buffer textures, (f) push constants (unused by vanilla) -> `setBytes`.
- **Uniform mapping:** UBO-only for numeric data. Vanilla blocks (all `layout(std140)`): `Globals`, `Projection`, `DynamicTransforms`, `ChunkSection`, `TerrainUniform`, `Fog`, `Lighting`, `CloudInfo`, `LightmapInfo`, `SpriteAnimationInfo`, post-effect UBO groups by name (see `BindGroupLayouts.java:L9-36` + jar:`include/*.glsl`). Samplers are named `Sampler0/1/2`, `InSampler`, `DepthBoundsSampler`, `Coeff0/1`, `DissolveMaskSampler`, `GlintSampler`, `Sprite`, `CurrentSprite/NextSprite`. **Names are the contract**: `RenderPass.setUniform(String name, ...)` looks up by name in `FrontendRenderPipeline.uniformIndices`. No loose uniforms (glslang with Vulkan semantics rejects non-opaque uniforms outside blocks) => anything like Iris' loose `uniform float frameTimeCounter;` cannot be compiled by this pipeline.
- **Push constants:** supported by API (`withPushConstantSize`, <=128 B, `CreateInfo.pushConstantsSize`, `RenderPassBackend.pushConstants`) but **no vanilla pipeline uses them** (grep `withPushConstantSize`: none in `net/minecraft`). VK uses `vkCmdPushConstants` stage ALL; GL emulates via a transient UBO named `_push_constants` (`GlCommandEncoder.java:L549-560`, `GlProgram.java:L64`).
- **Samplers/bindings:** binding = dense index into `CreateInfo.uniforms` (not the GLSL binding); `setUniform(index, TextureViewAndSampler)`; the SPIR-V image type tells 2D vs Cube (a cube sampler is bound to a view of a `USAGE_CUBEMAP_COMPATIBLE` texture). Sampler `texture()`/`textureLod`/`textureGrad`/`texelFetch` all used (jar:`include/texture_sampling.glsl`, `core/oit_composite.fsh`). Depth textures are sampled as plain `sampler2D` (e.g. jar:`core/blit_depth.fsh`: `texture(InSampler, uv).r`; `integrate_depth.fsh`: `texelFetch(InSampler, ivec2(gl_FragCoord.xy), 0).r`), i.e. SPIR-V image `Depth=0` bound to a D32_FLOAT texture. In Metal this means binding a depth-format MTLTexture to `texture2d<float>` (legal? Hypothesis: works; verify) or forcing `depth2d` in MSL via spvc.
- GLSL features vanilla uses that matter to the MSL path: `gl_FragDepth` writes (5 shaders -> `[[depth(any)]]`, kills early-Z in those passes), `gl_PointSize` (`debug_point.vsh` -> `[[point_size]]`), `gl_FragCoord`, `gl_VertexIndex`, `discard`, `dFdx/dFdy`, `textureGrad`, `isamplerBuffer`, constant arrays, bit ops. No `gl_InstanceIndex` use in core shaders (instancing is via vertex attributes), no geometry/tess, no `gl_ClipDistance`, no `invariant`.
- **Async/threading:** `GlslCompiler` pools shaderc compilers, thread-safe (`acquireCompiler synchronized`). `compilePipeline` runs on `Util.backgroundExecutor`.

### 5.1 `GpuFormat` (`RP/api/GpuFormat.java:L3-125`, 54 entries) (Verified)
8/16-bit UNORM/SNORM/UINT/SINT with 1-4 components (incl. 3-component RGB8/RGB16 which Metal textures lack but are only meaningful as vertex formats), 32-bit UINT/SINT/FLOAT with 1-4 components, 16-bit FLOAT 1-4, `RGB10A2_UNORM/UINT`, `RG11B10_FLOAT`, depth/stencil: `D32_FLOAT`, `D32_FLOAT_S8_UINT`, **`D24_UNORM_S8_UINT` (not available on Apple Silicon Metal)**, `D16_UNORM`, `S8_UINT`. `blockSize()` = componentSize*count (OPAQUE_* = 1 component of that size). Formats actually referenced by vanilla Java (grep `GpuFormat\.`): RGBA8_UNORM(22), RGBA32_FLOAT(6), RGBA16_FLOAT(4), D32_FLOAT(4), RG32_FLOAT, RG16_SINT, R8_SINT (cloud texel buffer), R32_FLOAT, RGBA8_SNORM, RGB32_SINT, RGB32_FLOAT. So the practical texture set is {RGBA8_UNORM, RGBA16_FLOAT, RGBA32_FLOAT, R8_UNORM?, D32_FLOAT}; other formats can be stubbed with `IllegalArgumentException` as GL does for unmapped ones (`GlDevice.createTexture L270-272`). - `GpuFormat.hasColorAspect/hasDepthAspect/hasStencilAspect` drive aspect masks.

### 5.2 Usage flags (Verified)
- Texture (`GpuTexture.java:L11-15`): `COPY_DST=1, COPY_SRC=2, TEXTURE_BINDING=4, RENDER_ATTACHMENT=8, CUBEMAP_COMPATIBLE=16`. Main targets use 15. VK mapping (`VulkanConst.textureUsageToVk L18-45`): RENDER_ATTACHMENT -> COLOR or DEPTH_STENCIL attachment by format aspect; TEXTURE_BINDING -> SAMPLED; COPY_* -> TRANSFER. => Metal `MTLTextureUsage.renderTarget` / `.shaderRead`; copies need no usage flag. Cube: 6 layers exactly.
- Buffer (`GpuBuffer.java:L10-19`): `MAP_READ=1, MAP_WRITE=2, HINT_CLIENT_STORAGE=4, COPY_DST=8, COPY_SRC=16, VERTEX=32, INDEX=64, UNIFORM=128, UNIFORM_TEXEL_BUFFER=256, INDIRECT_PARAMETERS=512`. Magic numbers appear in callers (`createBuffer(..., 32, ...)` = VERTEX, `128` = UNIFORM, `130`=UNIFORM|MAP_WRITE for ring buffers in `PostPass.java`).
- Mapping semantics (`GpuBuffer.map(offset,length,read,write)` + `MappedView(slice, ByteBuffer data, Runnable onClose)`): requires MAP_READ if read, MAP_WRITE if write; at least one; range inside buffer; <2 GiB; ref-counted; close of the view unmaps; closing a buffer with live mappings throws (`VulkanGpuBuffer.java:L126-175`). **Persistent mapping is not required by the API** (map/unmap per use is the contract); `features.persistentMapping` only enables the persistently-mapped `StagingBuffer` optimisation. Mapped memory must be coherent with GPU reads of later-recorded commands (VK uses coherent host-visible; no flush call exists). On Apple Silicon: `MTLStorageModeShared` and `buffer.contents()` pointer, never "unmap".
- Write-only mapped UBO ring buffers (`MappableRingBuffer`, `Lightmap.java:L66`, `PostPass.java:L118`) are updated every frame and read by that frame's passes; the backend must make sure a buffer rewritten on the CPU next frame is not still being read by the GPU from the previous frame - vanilla relies on the 2-in-flight `submit()` wait plus ring buffers of depth >=3 (`MappableRingBuffer`).

### 5.3 Draw/indirect formats (Verified)
- `drawIndexedIndirect`: records must be 20-byte `{indexCount, instanceCount, firstIndex, vertexOffset(int32), firstInstance}` (`RenderPass.INDIRECT_INDEXED_DRAW_SIZE=20`; frontend asserts via `VkDrawIndexedIndirectCommand.SIZEOF`, `FrontendRenderPass.java:L288`) - identical layout to `MTLDrawIndexedPrimitivesIndirectArguments` (`indexCount, instanceCount, indexStart, baseVertex, baseInstance`). `drawIndirect`: 16 B = `MTLDrawPrimitivesIndirectArguments`. Commands offset must be a multiple of 4. `drawCount>1` only if `features.multiDrawIndirect`; limit `maxDrawIndirectDrawCount`.
- Index buffer: `IndexType.SHORT(2) / INT(4)` only; bound at offset 0 (slice offset is expressed through `firstIndex`, see `LevelRenderer.java:L797` `firstIndex = indexBufferOffset / bytes`). Metal indexed draws want `indexBufferOffset` bytes: compute `firstIndex*stride`.
- `vertexOffset` = baseVertex (signed, e.g. section vertex buffer sub-allocation offset / vertexSize, `LevelRenderer.java:L800`). Metal `baseVertex` OK.

## 6. VulkanBackend/VulkanDevice details, and macOS stance

- **GL-isms handled in Vulkan:**
  - Clip-space depth: shaders/Java use zero-to-one (isZZeroToOne=true) and reverse-Z; no shader-side fixups needed.

(Inferred from VK code + shaders.)
  - Winding: compensated by CLOCKWISE front face (Inferred).
  - Instance index: with `shaderDrawParameters` the macro `RENDERPEARL_INSTANCE_INDEX_INCLUDES_BASE_INSTANCE` is defined (VK `gl_InstanceIndex` includes baseInstance); Metal `instance_id` also includes base instance (Hypothesis).
  - Dynamic state: viewport + scissor only (`pDynamicStates(stack.ints(1, 0))` = SCISSOR, VIEWPORT; `VulkanRenderPipeline.java:L309-312`). No dynamic blend/depth-bias state; one VkPipeline per pipeline (x2 if no depth state).

## 9. Level rendering, terrain, transparency, framegraph

### 9.1 Frame structure (Verified, `LevelRenderer.render` `LevelRenderer.java:L190-300`)
`FrameGraphBuilder` (CPU-side pass ordering/culling + `CrossFrameResourcePool` for transient `RenderTarget`s; `FrameGraphBuilder.java`, `CrossFrameResourcePool.java`) -> passes: `clear` (`clearColorAndDepthTextures(main color,fog color, main depth, 0.0)`), sky pass, `main` pass, entity-outline post chain, etc.; each pass `executes(Runnable)` creating one or more `RenderPass`es. **The framegraph conveys no GPU barriers/aliasing to the backend**; it only decides *when* RenderTargets (2D textures with usage 15-ish) are allocated/cleared (`RenderTargetDescriptor.prepare` clears via `clearColor/DepthTexture` on acquire, `RenderTargetDescriptor.java:L16-26`) and freed (pooled up to N frames). Backends see ordinary createTexture/close + clears.
- Typical pass shapes: `createRenderPass(label, colorView, Optional<clearColor>, depthView?, OptionalDouble clearDepth)`; MRT only in OIT.

### 9.2 Terrain draw paths (Verified)
- `LevelRenderer.prepareChunkRenders` (L823-876) -> `ChunkSectionsToRender.DrawSeparate` (`ChunkSectionsToRender.java:L161-195`): sets pipeline per `ChunkSectionLayer` (`layer.pipeline(false)`), `renderPass.drawMultipleIndexed(draws, defaultIndexBuffer(sequential quad IBO), type, dynamicUniforms=["ChunkSection"], sectionUbos)` -> N x (`setVertexBuffer(0)`, `setIndexBuffer` if changed, `setUniform("ChunkSection", ubo slice)`, `drawIndexed(count,1,firstIndex,baseVertex,0)`).
- `LevelRenderer.prepareChunkRendersIndirect` (L911-976) -> `DrawIndirect` (`ChunkSectionsToRender.java:L105-159`): `layer.pipeline(true)` = `*_TERRAIN_MULTIDRAW` pipelines (define `MULTIDRAW_TERRAIN`, vertex binding 1 `CHUNK_DATA_INSTANCED` stepRate=1: `ChunkPosition` RGB32_SINT + `ChunkVisibility` R32_FLOAT, `DefaultVertexFormat.java:L33-36`; jar:`core/terrain.vsh` consumes them as attributes 4,5), writes the 20-byte indirect records via `RenderSystem.getDynamicUniforms().writeChunkSectionCommands` (record `firstInstance` = section info index), `setVertexBuffer(1, chunkSectionInfos)`, `setVertexBuffer(0, region vertexBuffer)`, `setIndexBuffer(...)`, then `drawIndexedIndirect(slice, min(remaining, maxDrawIndirectDrawCount))` looped. Selection: `multiDrawIndirectAvailable = maxDrawIndirectDrawCount>0 && nonZeroFirstInstance && !multiDrawIndirectHasKnownIssues` (`LevelRenderer.java:L186-189`) AND `Minecraft.multiDrawIndirect` (default true, `Minecraft.java:L387`) via `LevelExtractor.java:L236`. Translucent layers: with classic transparency, sorted back-to-front draw groups are reversed (`respectTranslucentOrder` true) -> draw order within the indirect buffer matters (Metal indirect draws execute in order).
- Terrain section meshes are built on CPU (SectionCompiler etc.) and uploaded into big shared region buffers (`UberGpuBuffer`/`TlsfAllocator` in `blaze3d/vertex`): a backend sees `writeToBuffer`/`copyToBuffer`/`copyBufferToBuffer`-style uploads into large (GiB-scale?) buffers. Unverified sizes. Check `UberGpuBuffer` before choosing Metal buffer-size limits (`maxBufferLength`).
- Sodium/Iris replace all of this and talk raw GL (see 10).

### 9.3 Transparency modes (Verified)
- Option `improvedTransparency` (`Options.java:L231-235`, default **false**, tooltip key `options.improvedTransparency.oit.tooltip`), `GameRenderer.useImprovedTransparency()` = option && !wireframe terrain (`GameRenderer.java:L871-873`). Debug key `keyDebugSwitchTranslucencyMode`.
- **Classic** (`executeClassicTransparency`, `LevelRenderer.java:L695+`): single main pass: solid terrain+features, then translucent terrain (blend `TRANSLUCENT`), then entities/particles/clouds/weather with ordinary alpha blending in sorted order (CPU resort of translucent sections, `resortTransparency`).
- **OIT** (`executeOit`, L568-693): constants `OIT_COEFFICIENT_COUNT=8`, `OIT_TRANSMITTANCE_TARGET_COUNT=2` (RGBA16F each), wavelet rank 2 (`LevelRenderer.java:L112-114`, `RenderPipelines.OIT_SNIPPET L34-39`). Per `OitStage` (DEPTH_BOUNDS -> TRANSMITTANCE -> ACCUMULATE): terrain translucent layer, then entity/feature/world-border/weather OIT pipelines, then clouds. Passes (`OitRenderPassProvider`):
  1. DEPTH_BOUNDS: color RGBA32F (clear = DEPTH_BOUNDS_CLEAR_COLOR), blend MAX, depth test GREATER_THAN_OR_EQUAL, no depth write, discards alpha<0.01. After it a "BLIT_DEPTH_BOUNDS" + "OIT_DEPTH_BOUNDS_CULL" fullscreen pass produces `depth_bounds_culled` and writes `gl_FragDepth`.
  2. TRANSMITTANCE: **2 MRT RGBA16F, ADDITIVE blend, depth attachment (test-only)**, fragment samples `DepthBoundsSampler`.
  3. ACCUMULATE: RGBA16F ADDITIVE, samples `Coeff0/1` + depth bounds.
  4. Composite `OIT_COMPOSITE` fullscreen draw into main color with premultiplied-style blend and **writes gl_FragDepth** (jar:`core/oit_composite.fsh`).
  Extra render targets: `depth_bounds`, `depth_bounds_culled` (RGBA32F), 2x transmittance, accumulate, `cloud_depth` / `terrain_depth` (D32F). Also a "water mask" depth pass that copies main depth with a `gl_FragDepth` write (`BLIT_DEPTH`).
  Needs: multi-render-target passes (n=2 color + depth), depth-only passes (no color attachment: `RenderPassDescriptor` with only depth, e.g. "Water mask", "Integrate always on top depth"), sampling of previously rendered float targets with NEAREST, MAX/ADD blending on float formats, shader depth output.
- Always-on-top gizmos path: `executeAlwaysOnTop` renders with `OptionalDouble.of(0.0)` depth clear into a separate depth texture and re-integrates via `INTEGRATE_DEPTH` (`gl_FragDepth = depth` with `discard` when 0).
- Depth-only render pass (no color attachments) and passes with unused (null) color slots are API features Metal can do natively.

### 9.4 Post-effect JSON (the closest vanilla gets to "shader packs")
`assets/<ns>/post_effect/<id>.json` (`ShaderManager.POST_CHAIN_ID_CONVERTER`, `PostChainConfig.java`): `{"targets": {name: {width?,height?,persistent?,clear_color?}}, "passes": [{vertex_shader, fragment_shader, inputs:[{sampler_name, target|location, bilinear?, use_depth_buffer?}], output, uniforms:{BlockName:[{name,type,value}]}}]}`. Passes become `RenderPipeline`s compiled lazily by `PipelineCache` (full-screen triangle `core/screenquad.vsh`, UBOs generated std140 from the JSON `UniformValue`s with `Std140Builder`, `PostPass.java:L35-80`). Examples shipped: blur, creeper, entity_outline, invert, spider (jar listing). Hooks: `GameRenderer.appliedPostEffects`, `END_OF_FRAME_POST_EFFECT` (id `minecraft:...` loaded if present), entity-outline chain. This is resource-pack extensible, single-sample, fragment-only, inputs are named color/depth targets or textures, output a single target. No compute, no mip-chain, no MRT output per pass (single `output`), no loose uniforms, no geometry shaders.

## 11. What a Metal `GpuDeviceBackend` must implement (checklist)

1. `GpuBackend`: `getName()="Metal"`, `loadLibrary/unloadLibrary` (no-op, `SDL_Metal` ships with SDL), `createWindow` (`SDL_CreateWindow(..., SDL_WINDOW_METAL | flags)`), `createDevice` -> `new FrontendGpuDevice(new MetalDevice(...))`. Plug in via mixin on `PreferredGraphicsApi.getBackendsToTry`.
2. `GpuDeviceBackend`: device, queue, `DeviceInfo` (isZZeroToOne=true; limits: maxAnisotropy 16, `minUniformOffsetAlignment` 256 recommended for constant buffers on macOS - Hypothesis, maxTextureSize 16384, maxColorAttachments 8, maxDrawIndirectDrawCount 1 if looping or large if ICB, `maxMultiDrawDirect...`=0; features: wireframe=true, shaderDrawParameters=true, multiDrawDirect*=false, multiDrawIndirect=false (or true if ICB), drawIndirect=true, nonZeroFirstInstance=true (Apple GPU family >= Apple3? baseInstance in indirect needs MTLGPUFamilyApple3/Mac2), persistentMapping=true; hints: writeToBufferIsSlow=false, isExplicitDepthRequired=true on Apple Silicon), samplers, textures (+views), buffers (shared storage), `compilePipeline` (SPIR-V->MSL->MTLLibrary->RPS; thread-safe), timestamp pool (can be empty), `getTimestampCalibrationOffset`.
3. `CommandEncoderBackend`: one MTLCommandBuffer per frame (or per section), `submit()` = commit + wait for frame N-2 via MTLSharedEvent or completion handler (5 s timeout semantic optional), deferred destruction (2 frames) for all closeable resources, `TransientMemory`, render pass creation (descriptor mapping with clear/load, store always, null colorAttachment slots, depth-only passes, renderArea -> scissor/viewport + full attachment viewport), clear ops (implement as render passes with `loadAction=.clear` incl. region+mip variants -> scissored passes), buffer/texture copy ops via blit encoder (`writeToTexture` rows tightly packed, `copyBufferToTexture` source width as row length), readback callback after completion, fences, timestamps.
4. `RenderPassBackend`: dirty-tracked uniform table -> `setVertex/FragmentBuffer(offset)`, `setFragmentTexture/SamplerState`, texel buffers via `MTLBuffer.makeTexture`; `setPipeline` (rebind all dirty state and per-pass `hasDepth` variant, depth-stencil state, cull, front-face, depth bias, fill mode), vertex/index buffers, scissor enable/disable (disable restores renderArea, not full texture), `draw`, `drawIndexed`, `drawIndexedIndirect` (loop or ICB), TRIANGLE_FAN expansion, the `RenderPassBackend.setIndexBuffer` offset convention.
5. `GpuSurfaceBackend`: CAMetalLayer lifecycle, `acquireNextTexture` (nextDrawable; throw `SurfaceException` on nil/minimized), `blitFromTexture` (format/Y/swizzle-correct pass), `present` (presentDrawable on the command buffer), `supportedPresentModes={FIFO,IMMEDIATE}`.
6. SPIR-V -> MSL (spvc): resource bindings by dense index, flip-Y policy, fix up combined image samplers, depth textures, `[[depth(any)]]`, point size, texel buffers, UBO std140 packing, `base_instance`/`instance_id` semantics, vertex attribute remap, fragment output remap for MRT (location -> color index), and shader caching (pipelines are compiled at resource reload: ~150 required + dynamic).

### 11.1 Hardest semantic gaps (ranked)
1. **Implicit full-memory-dependency ordering** between all commands (no barrier API). Metal hazard tracking on untracked/heap resources, multiple encoders per frame, and UBO ring buffers rewritten each frame must be made to behave like VK's "global barrier after every op".
2. **Y/winding/NDC convention** (section 5/6): reproduce "row 0 == clip y=-1" so `gl_FragCoord`, scissor, post-chain UVs, `texelFetch(gl_FragCoord)` in OIT, and the final flip all agree. Metal NDC y-up + origin top-left is the opposite of what the frontend's textures assume; SPIRV-Cross MSL option `flip_vert_y` (SPVC_COMPILER_OPTION_FLIP_VERTEX_Y) + `frontFacingWinding` + final-blit policy must be tested together (Hypothesis on exact winding).
3. **Reverse-Z + depth invariance on Apple Silicon**: OIT shaders write `gl_FragDepth = gl_FragCoord.z` (disables early-z in those passes). Depth bias units differ.
4. **Multi-draw indirect** (terrain default path): needs ICB or per-draw loop; Metal `baseInstance` + per-instance vertex stream semantics must match `firstInstance` indexing the chunk info stream (`stepRate=1` on binding 1).
5. **TRIANGLE_FAN** and the "QUADS/LINES as triangle lists with synthesized index buffers" conventions; non-indexed `draw` of fans.
6. **Async pipeline compile contract** (worker thread vs render thread `finishCompile`) and **~150 pipeline specializations** each with/without depth variant and MRT formats; compile time of shaderc + spvc + Metal compiler at every resource reload (resource-pack shader overrides trigger full recompile).
7. **Lifetime semantics**: close-while-in-flight legal; readback callbacks; fences keyed on submit index; mapped buffers rewritten while previous frames still in flight.
8. Texture format gaps (RGB8/D24S8/3-component), depth-texture-as-`sampler2D` binding, texel buffers (`R8_SINT`, offset/size alignment, entire-buffer only), anisotropy semantics, LINEAR mip filter.
9. Everything the frontend only validates under `STRICT_VALIDATION` (IDE): production code gets raw input.

Vanilla exposes only these "shader-pack-like" surfaces: (a) resource-pack GLSL replacement for every `core/*.vsh|fsh` and `include/*.glsl` (330 + Vulkan-flavored GLSL, UBO-only), (b) `post_effect/*.json` fullscreen pass chains (section 9.4), (c) `RenderPipelines` registry (static). There is no hook to inject extra passes into LevelRenderer's frame graph other than mixins.
Missing for Iris-style packs (all Verified-absent in the API): compute pipelines / compute encoder; geometry & tessellation stages; SSBOs/storage images/image load-store/atomics; loose `uniform` variables (Iris custom + builtin uniforms are loose); `sampler2DShadow` / compare samplers (GpuSampler has no compare state, only REPEAT/CLAMP, NEAREST/LINEAR, aniso, maxLod); clamp-to-border/mirror; 3D / array / cube-array textures and non-2D views; mip generation (`glGenerateMipmap` equivalent) - possible via per-mip render passes using `createTextureView(tex, baseMip, 1)` + `copyTextureToTexture`; MSAA; stencil; per-attachment blend states (all non-null blend functions must be equal; Iris uses `DRAWBUFFERS`/`blend.<buffer>` configs); blend constants; per-pass color-write masks other than pipeline-level; texture formats beyond the 54 enum entries (no sRGB, no compressed); 8 color targets max in API (`MAX_COLOR_TARGETS=8`) vs Iris colortex 0-15; viewport control (fixed to attachment, only scissor is settable - shadow map and render-scale (viewport smaller than the attachment) need `renderArea`); depth-only pass supported; no timer/occlusion queries (only timestamps).
Sodium 0.9.x and Iris 1.11.x in the local checkouts both import `com.mojang.renderpearl` extensively (59 and 158 files respectively) and Iris still has 87 files with raw `org.lwjgl.opengl` (downstream grep): they are tightly coupled to GL; a Metal backend with the Iris ecosystem needs those mixin targets (GlDevice/GlCommandEncoder/GlRenderPass) replaced by renderpearl-API equivalents, which this API cannot express for compute/loose-uniform/shadow cases.

## 13. Doc-vs-code / surprises worth knowing
- The package name `renderpearl` is not "Blaze3D"; `com.mojang.blaze3d.*` is now only platform + game-side helpers (RenderSystem, Window, pipeline/RenderTarget, framegraph, vertex builders). The old `GpuDevice/CommandEncoder/RenderPass/RenderPipeline` of 1.21.x live in `renderpearl.api` with changed shapes: `BindGroupLayout` (named uniform groups), `ColorTargetState[]` MRT, `DepthStencilState`, `VertexFormat` per binding slot with step rate, `TransientMemory`, `GpuSurface`.
- `GpuFence.awaitCompletion(timeoutNS)` but callers name the param `timeoutMs` inside backends; Vulkan passes it straight to `vkWaitSemaphores` (nanoseconds). Backend must treat it as ns.
- `FrontendCommandEncoder.writeTimestamp` validates `index <= pool.size()` (off-by-one: allows index==size) while render pass has the same check.
- `PreferredGraphicsApi.getBackendsToTry()` constructs *both* backend objects each call (cheap, no native work until `loadLibrary`).
