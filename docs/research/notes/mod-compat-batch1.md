  - Shaders are `#version 450` with `layout(location=...)` for 26.3 (`assets/reglass/shaders/core/blit_fullscreen.vsh:1-5`, `program/liquid_glass_gui.fsh`, `program/blur.fsh`). `bg.fsh`/`bloom.fsh` are still `#version 150` (legacy-branch only; not referenced from Java, grep found no `liquid_glass_pre`/`program/bg` use in `src`). Uses only `textureSize` (`bg.fsh:147`, `liquid_glass_gui.fsh:197`); no `texelFetch`, `dFdx`, `gl_FragDepth`.
  - Draws via a GUI element renderer (`gui/LiquidGlassGuiElementRenderer.java`, `LiquidGlassGuiElementRenderState.java`) plus `GuiRendererMixin` (`mixin/widgets/`), with a shared quad VBO created by `RenderSystem.getDevice().createBuffer(..., 32, byteBuffer)` (`GuiRendererMixin.java:55`).

(2) `GLFW.*` in `LiquidGlassUniforms`/`PlatformInput`: need to confirm only constants/`SDL*` calls are executed; `grep` shows `SDLTimer`/`SDLMouse` being used for the actual calls. ## 2. Meshelium ("mesh shader rendering")

- Repo / commit: `ded811/Meshelium` main `e4d0a3f` "1.6.2", 2026-09-24. Single branch. One source tree, `mc_canonical=26.3` with derived 26.2 (`gradle.properties`, `versions/README.md`, `versions/mc26.3.properties`: Fabric loader 0.19.5, Fabric API 0.161.0+26.3, Sodium 0.9.2). Licence **LGPL-3.0-only**; some shader logic is derived from Nvidium (MCRcortex, LGPL-3.0), stated in each shader header (e.g. `assets/meshelium/shaders/terrain.mesh:1-12`). **Verified.**
- What it is (Verified, `README.md`, `docs/TECHNICAL.md`): a terrain renderer for **vanilla's Vulkan backend** (and a Sodium adapter) that draws terrain with **`VK_EXT_mesh_shader`** task+mesh+fragment pipelines, a GPU-side per-section cull in the task shader (`shaders/terrain.task`), a software-ish occlusion pass (half-res depth downsample + section/region box raster, `shaders/occlusion/*`, `vk/TerrainOcclusion.java`), plus unlocking render distance up to 64 (vanilla-only) / 96 (Sodium) and optional far-field shells (`farfield/*`), smart/solid leaves, greedy meshing, memory trim.
- GPU features needed (Verified):
  - **Not** `GL_NV_mesh_shader`: README "It targets `VK_EXT_mesh_shader` rather than the NVIDIA dialect"; shaders are `#version 460` EXT dialect (`terrain.mesh:3`). No GL code anywhere.
  - `VK_EXT_mesh_shader` (meshShader+taskShader) as a vanilla `FeatureSet` (`versions/mc26.3/common/.../vk/MeshShaderFeatureSets.java:50-55`), `fragmentStoresAndAtomics` for occlusion, optional `VK_EXT_conditional_rendering`, `VK_EXT_conservative_rasterization`, `VK_EXT_memory_budget`, `VK_KHR_push_descriptor` (vanilla enables), dynamic rendering (`TECHNICAL.md:~488`, `MeshShaderDeviceSupport.java:63-206`).
  - Reads inter-workgroup primitive-order guarantee of `VK_EXT_mesh_shader` for translucent draw order (`terrain.mesh` header, `TerrainDrawPipeline.java:49`).
- Does it replace Sodium's terrain renderer? **Verified: partially / by adapter.** Standalone (no Sodium) it cancels `ChunkSectionsToRender.renderGroup` at HEAD and taps vanilla section compile (`MesheliumGate.java:~140`, `SectionCompilerMixin`, `ChunkSectionsToRenderMixin`). With Sodium present (which it supports as of 1.6.x, Sodium 0.9.2 only) it does **not** replace Sodium's build path; it mirrors Sodium's region/section buffers (`SodiumMirrorGpu`, `MesheliumRegionMirror`, mixins `RenderRegionManagerMixin`, `RenderSectionManagerMixin`, `VKIndirectContextMixin`, `VulkanGpuBufferDirectMixin` in `sodium/src/.../mixin/`) and draws opaque terrain through its own mesh pipeline instead of Sodium's draw; on any decline it hands back to Sodium (`MesheliumSodiumMixinPlugin.java` javadoc "Meshelium reads Sodium's buffers and writes none of Sodium's state"). Kill switch: `-Dmeshelium.sodium.adapter=false`.
- Does it run on macOS today? **No, by the author's declaration and by construction.** `TECHNICAL.md:479-482`: "macOS is out of scope permanently, because MoltenVK does not translate mesh shaders"; README "Sorry, no Mac". Code-level: gate is `"Vulkan".equals(info.backendName())` (`MesheliumGate.java:331`) and everything else (`else decided = State.OPENGL`) is dormant. Only one GPU ever measured (RX 9070 XT, `TECHNICAL.md:335`).
- GL call-site count: **0**. Vulkan API use: 34 files import `org.lwjgl.vulkan` / `renderpearl.backend.vulkan` (it records its own `VkGraphicsPipelineCreateInfo`, command buffers, descriptor writes, etc., via mixins `VulkanCommandEncoderMixin/Accessor`, `VulkanDeviceMixin`, `VulkanBackendMixin`, `VulkanFeatureSetsMixin`, `VulkanRenderPassStateMixin`, `VulkanRenderPassAccessor`).
- Co-installation with Metallium (user wants parallel install) (Strongly inferred, not run):
  - **Loads:** it depends on `fabricloader>=0.19.0`, `fabric-api`, `minecraft` only (`fabric/src/main/resources/fabric.mod.json:27-30`); Sodium is soft. All Vulkan-targeting mixins target classes that exist in the vanilla jar regardless of backend, and they only execute when Vulkan code runs, so they should apply cleanly and sit idle on Metal. Mixin config uses `defaultRequire:1` (`meshelium.client.mixins.json`), fine because targets exist.
  - **Dormant behaviour:** every functional hook checks `MesheliumGate.state() == VULKAN_MESH_SHADERS` (e.g. `LevelRendererMixin.java:177,289,369,451`, `SectionRenderDispatcherMixin.java:40`, `SectionCompilerMixin.java:119`, `MesheliumExtendedRd.java:583`). On Metal the gate resolves to `OPENGL` (non-"Vulkan" backend name), i.e. fully dormant.
  - **Known wart (Strongly inferred):** in the `OPENGL` state it shows the first-run popup "Enable Vulkan / Prefer Vulkan" (`MesheliumGate.java:733-748`), which would be actively wrong advice on Metallium; mitigation: a compat mixin (b) setting the config flag `showVulkanPrompt=false` or setting the Metallium device `backendName()` such that the popup path is skipped. Cheap. Also the Sodium-side mixins (`RenderRegionManagerMixin`, run-cache bookkeeping) are applied whenever Sodium is present even if the adapter is not armed (Hypothesis: small CPU/memory overhead); recommend `-Dmeshelium.sodium.adapter=false` in Metallium launcher profiles.
  - **Render-distance extension is gated** on VULKAN_MESH_SHADERS or SODIUM_PRESENT (`MesheliumExtendedRd.java:583-584`); `SODIUM_PRESENT` state may unlock the extended slider (up to 96) even when the adapter is not drawing (Hypothesis, needs a run). Unlocking RD without the mesh path is a risk on Metal (memory).
- Predicted status: **(d) as a renderer** (needs Vulkan + VK_EXT_mesh_shader; not translatable by MoltenVK; there is no GL/Metal path). As a co-installed jar: **(a)/(b)** (dormant; one tiny compat mixin or config default for the popup). Required work: ~2-4 h for the popup/config suppression and a run-through with Sodium installed; or document `showVulkanPrompt=false` in the Metallium README.
- Are its ideas useful for Metallium? **Yes, selectively. The mesh shader itself is the smaller part.**
  - Metal facts (Hypothesis unless stated; verify against Apple docs before building): Metal 3 object/mesh shaders exist (`MTLMeshRenderPipelineDescriptor`, `drawMeshThreadgroups`, optional indirect dispatch); available on Apple-silicon (Apple7+, M1/A14 and newer) and Metal 3 AMD/Intel Macs. They are the direct analogue of task/mesh/fragment. Existing in-repo evidence: MetalRender ships `mesh_terrain.metal` as an optional path (`metalrender.md:177`; ideas only, licence), and `nvidium-embeddium-frapi.md:144` already flags the Metal-MDI problem.
  - **Does not transfer:** Meshelium's Vulkan plumbing (own VkPipeline creation, descriptor/push-constant layout, `VK_EXT_conditional_rendering`, `VK_EXT_conservative_rasterization`, memory-budget probing). SPIR-V `MeshEXT` capability to MSL via SPIRV-Cross is Hypothesis-unsupported (SPIRV-Cross mesh shader support is not something I verified), so a Metal path means hand-written MSL object/mesh functions plus a Metallium extension API, because renderpearl's frontend only knows vertex+fragment pipelines (`vanilla-renderpearl.md` §0.3-0.4: "no compute, geometry/tess"; mesh topology not in `RenderPipeline`). That is category (c) work (a Metallium-private pipeline type reachable from a Sodium-adapter-like hook), not a vanilla-pipeline tweak.
  - **Transfers conceptually (algorithms, all CPU/MSL-side, no GL):** (1) per-section GPU frustum+facing-bucket culling in the object (task) stage with a payload bin table (`terrain.task`; derived from Nvidium so re-implement from the idea, not the file); (2) quad-expanding mesh stage with sub-pixel primitive culling (matches Nvidium's mesh shader, `nvidium-embeddium-frapi.md:117`); (3) the translucent ordering note (Metal makes no inter-threadgroup primitive-order guarantee comparable to EXT: Hypothesis, so translucency probably stays on the vertex pipeline or needs a sorted-by-threadgroup scheme); (4) the arena/region-run table + upload seam (`terrain/TerrainArena`, `SegmentedManager`, `SodiumMirrorGpu`) is backend-neutral bookkeeping and the closest thing to a reusable design; (5) memory model: on Apple unified memory the VRAM-pressure policy (`MesheliumVramState`, `MeshShaderDeviceSupport` memory budget) maps to `recommendedMaxWorkingSetSize`, but "trim idle terrain memory" is less important.
  - **Backend-independent features worth separate evaluation:** far-field shell meshing (`farfield/*`), greedy meshing, smart/solid leaves, extended render distance (CPU/server side `ChunkMapMixin`, `DistanceManagerMixin`). These do not need mesh shaders; they were validated on one Vulkan GPU only.
  - **Value judgement (Hypothesis):** Apple GPUs are tile-based deferred renderers with hidden-surface removal and cheap draws via ICBs, so the win of per-section occlusion raster (Meshelium's biggest lever at RD 48+) is likely smaller on Metal than on desktop discrete GPUs; a Metal ICB/indirect-draw terrain path (frontend "Setting `multiDrawIndirectHasKnownIssues`" note, `vanilla-renderpearl.md` §0.6) probably captures most of the CPU-side gain first. Mesh shaders are a phase-2 experiment once the baseline Sodium-on-Metal path is profiled.
  - **Licence note:** Meshelium is LGPL-3.0 and itself derives from Nvidium LGPL-3.0. Per `CLAUDE.md`, treat as ideas-only unless the work is placed in an LGPL module; credit in README "Credits & licenses" row either way if ideas are used.

## Cross-cutting observations (for the Metallium compat docs)

1. All five mods have **zero raw GL**. Four of five are therefore (a) on Metal; the odd one out is Meshelium, which is hardware/API-gated (Vulkan mesh shaders), not GL-gated.
2. ReGlass is the only one that exercises backend features beyond vanilla's stock pipelines (custom 6-sampler fragment shader, backdrop copy). Make it a Metallium regression test for (i) `copyTextureToTexture` of the main target, (ii) many samplers per stage, (iii) UBO `mapBuffer` writes.
3. Meshelium's gate treats "not Vulkan" as OpenGL, so the only collision is its "switch to Vulkan" popup. Suggest documenting `showVulkanPrompt=false` / `-Dmeshelium.sodium.adapter=false` or shipping a 1-class compat mixin.
4. Light Overlay needs an upstream or local port to 26.x before any test; Metal is not the blocker.
5. Nothing here needs `metallium-gl`. A Metallium extension API (custom pipeline types: mesh/object, indirect command buffers) would only matter for a future Metal-native mesh terrain path inspired by Meshelium/Nvidium, not for any compatibility goal in this batch.
