## 2. What it replaces / how it hooks

- Only the GPU abstraction (RenderPearl backend). Everything above (LevelRenderer, vanilla terrain meshing, chunk sections, entity/feature renderers, GUI) is vanilla. No GL interop, no IOSurface, no second window/layer; presentation directly into SDL's CAMetalLayer. [Verified]

## 4. Command buffers / sync / frames in flight

- One `MTLCommandQueue`, one open `MTLCommandBuffer` at a time (`Device::commands()` lazily creates, `MetalContext.mm:~101-128`); `submit()` (`MetalContext.mm:~255-320`) adds completed handler, commits. Java `MetalCommandEncoder.submit()` (`J/MetalCommandEncoder.java:41-56`) -> native submit, creates a `MetalFence` bound to that buffer, queues a Retirement (transient memory + copy-to-buffer callbacks), then `drain(false)`: non-blocking unless >3 pending, then waits up to 5 s (`:58-71`). [Verified]
- **3-deep ring**: `UploadFrame uploads[3]`, each guarded by `dispatch_semaphore(1)`; `commands()` waits on `uploads[serial%3]->available` (try-wait then 10 s timeout) and releases it in the command buffer's completed handler (`MetalContext.mm:83,107-118,265-314`). Upload arena (4 MiB min shared buffers) lives per ring slot; `UploadFrame` also owns ICB batches and stage-timing samples. [Verified]
- Drawable: `layer.maximumDrawableCount=3`, `allowsNextDrawableTimeout=YES`, `displaySyncEnabled = (present mode == FIFO)` (`MetalPresentation.mm:50-69`). `nextDrawable` is acquired in `acquireSurface` (called by frontend before the frame), presented via `presentDrawable` in the same command buffer as the final blit (`blitSurface`, `:117-137`). Present modes: FIFO, IMMEDIATE only (`MetalSurface.java:16-17`). Layer config does `dispatch_sync(main_queue)` when off-main (`:13-15`) — potential main-thread dependency [Hypothesis: harmless since SDL main thread is the MC render thread on macOS].
- Hazard tracking: resources untracked by default; ordering of encoders via a **single global `MTLFence`** (`encoderFence`, `waitForRenderFence/updateRenderFence`, `MetalContext.hpp:190-191,232-240`) => serial encoder chain, same pattern as Metallum. Opt-in `MINECRAFT_METAL_TRACKED_HAZARDS=1` uses tracked resources (`MetalContext.mm:74,196`). [Verified]
- Fences: `MetalFence` wraps `FenceState` mutex/condvar completed from the completed handler. Timeout handling = exception.
- Error handling: command buffer `status==Error` prints to stderr only (`MetalContext.mm:~287`); fence gets error string.
- Timestamps: `MTLCounterSampleBuffer` ring[3], resolved on completion (comment explicitly notes stale values from GPU blit resolve on tile-based GPUs, `MetalContext.mm:~290`). Optional per-stage timing (`MINECRAFT_METAL_RENDER_STAGE_TIMINGS=1`). ExecutionStatistics counters (submitted/completed buffers, GPU span, upload-ring blocked acquires, drawable acquire time). [Verified] Good diagnostics design.
- Offscreen present diagnostic (`MINECRAFT_METAL_OFFSCREEN_PRESENT=1`, `MetalPresentation.mm:42,71-95`): bypasses CAMetalLayer to measure throughput w/o display pacing. Useful idea.

## 5. Pipelines & shader handling

- **SPIR-V -> MSL at runtime via LWJGL SPIRV-Cross (`org.lwjgl.util.spvc`)**, same as Metallum. Vanilla's frontend GLSL->SPIR-V (shaderc) is reused: `BackendRenderPipeline.CreateInfo.shaders()[].module().spv()` (`J/MetalShaderCompiler.java:335-345`). No hand-written MSL for MC shaders. [Verified]
- Per pipeline: parse each SPIR-V with spvc, set entry point (rename to `main`), reflect UBOs + sampled images, check active interface vars (`Module` ctor `:335-402`), reject storage buffers/images (`:392-395`). MSL 2.3 (`MSL_VERSION 20300`), platform macOS, `texture_buffer_native`, `FLIP_VERTEX_Y=true`, optional `enable_frag_depth_builtin` (second fragment function without depth output for passes lacking a depth attachment) (`:489-523`). MSL string cache keyed by (base64 SPIR-V, stage, entry, bindings, emitDepth, arguments) — in-memory only, **no disk cache / no binary archive** (`mslCache` HashMap `:36`). `compile()` is `synchronized` (serializes concurrent compiles). [Verified]
- Fixed binding scheme: descriptor set 0 only; uniform buffers -> MSL buffer slots 16..29 (`bufferIndex=16`), push constants -> buffer 30 (`PUSH_CONSTANT_BUFFER`), textures/samplers -> indices 0..15, texel buffers -> texture slots after samplers up to 128 (`linkResources :177-239`). Vertex buffers occupy buffer 0..15. Limits throw IllegalArgumentException (14 UBO slots, 16 samplers). [Verified]
- Optional **argument-buffer path** (spvc discrete descriptor set 1 for textures/samplers at `[[buffer(29)]]`; sampler id +128) used only when `minecraftMetal.indirectCommandBuffers=true` (default false) because ICBs need argument buffers for textures; with automatic fallback to direct binding if translation throws (`:61-78`). [Verified]
- Pipeline state: native `Pipeline` holds `MTLRenderPipelineDescriptor` and lazily creates `variants` keyed by (depth fmt, color fmts) hash (`Pipeline::state`, `MetalContext.mm:~320`; key mixing is a weak multiplicative hash with no collision check [Hypothesis: collisions improbable but not impossible]).
- Math policy: `MetalPipelineMath` thread-local scope lets the shader loader request **Relaxed fast-math fragment compilation** for a single exactly-named pipeline; backend honours only on macOS 15+/Apple4+ and only if `SpirvMathPolicy.permitsRelaxedFragment(spirv)` (no precision decorations) (`J/MetalPipelineMath.java`, `J/SpirvMathPolicy.java`, `N/MetalCommands.mm:21-32,35-57`). Default `MTLMathModeSafe`; `preserveInvariance=YES` (needed for depth-prepass position invariance). Env `MINECRAFT_METAL_MATH_MODE` legacy override. [Verified]
- `MetalPassHints` (`J/MetalPassHints.java`): thread-local, one-shot "discard old color contents" proof (load action DontCare) for full-overwrite passes; capability string `color-attachment-load-discard`. Used by shader loader (`FullscreenOverwrite`). [Verified]
- Triangle fans: no fan topology in Metal => compute kernel `expand_triangle_fan` (`N/shaders/triangle_fan.metal`) — present on main; note `origin/codex/*` branches delete this file (diff stat) so topology handling differs by branch. [Verified diff stat; not examined further]
- Dumps: `-DminecraftMetal.dumpShaders=true` or on failure -> `debug/metal-shaders/*.vert.metal`.

## 6. Resource binding / draws / indirect

- `MetalRenderPass` caches uniforms Java-side and flushes dirty ones lazily per draw (`prepare()`, `J/MetalRenderPass.java:369-418`) via JNI `bindTexture/bindUniform/bindTexelBuffer`; pipeline change resets everything dirty. Native `RenderState` keeps arrays of 31 buffers/128 textures/16 samplers per stage and applies them at draw (`MetalContext.hpp:150-165`).
- **Draws are one JNI call each.** `multiDrawIndexed` / `multiDraw` (Sodium-style PointerBuffer variants too) just loop over `drawIndexed` (`MetalRenderPass.java:443-472`). `drawIndirect/drawIndexedIndirect` (vanilla 26.3 section indirect draws) go to native `drawIndirect` which by default loops `drawPrimitives/drawIndexedPrimitives` reading the indirect args on CPU from the shared buffer; optional ICB path when `count >= threshold(64)` && `<=16384` && `minecraftMetal.indirectCommandBuffers=true`: GPU compute `encode_indirect` fills an `MTLIndirectCommandBuffer`, then `executeCommandsInBuffer` — which **splits the render encoder** (suspendRender/resumeRender) around a compute encoder (`MetalCommands.mm:~237-300`, counters `indirectFirstDrawSplits/AfterDrawSplits`). A CPU-populated ICB variant (`MINECRAFT_METAL_CPU_ICB=1`) and an ICB reuse cache (`MINECRAFT_METAL_ICB_REUSE=1`) with "published CPU indirect snapshots" of mapped buffers exist (`Buffer::publishCpuIndirect`, `MetalContext.hpp:46-93`). All default OFF. [Verified]
- Storage: buffers `Shared` if mappable else `Private` (`MetalResources.mm:46`); textures `Private`; texel buffers via lazily created per-format texture views (`texelViews` map). Uploads (`writeBuffer/uploadTexture`) go through per-frame shared upload ring + blit encoders (not `replaceRegion`). Transient memory = persistent shared arenas retired by fence (`J/MetalTransientMemory.java`, 1 MiB blocks up to 1 GiB).
- Clears: implemented as fullscreen-triangle render pipeline (`clear.metal`) when not a render-pass load clear (`clearAll/clearMip`, partial-area clear support).
- Scissor clamped to render area (`MetalRenderPass.java:345-354`).
- Not supported: compute pipelines (RenderPearl has none), storage buffers/images, mesh shaders, MetalFX, Metal 4, heaps, residency sets, GPU-driven culling. [Verified by absence]

## 13. Ideas worth reusing for Metallium (ideas only unless MIT-copy is approved)

1. **Hash-keyed native extraction + per-pipeline MSL cache keyed by SPIR-V**; add what it lacks: persistent disk cache / `MTLBinaryArchive`, async compile (it serializes `compile()`).
2. **Fragment-depth variant**: second fragment function without depth output for passes lacking a depth attachment; `FLIP_VERTEX_Y`, `preserveInvariance` for depth-prepass vertex invariance (needed by Iris-style shadow/depth prepasses) (`MetalShaderCompiler.java:489-523`; `MetalCommands.mm:35-57`).
3. **Math-mode policy by exact pipeline name** (Safe vertex, Relaxed fragment only when SPIR-V has no precision decorations; macOS 15+/Apple4+) and `mathFloatingPointFunctions=Fast` — measurable win candidate for Iris packs; needs per-pack opt-in/validation.
4. **Attachment load-discard hint** for full-screen overwrite composite passes (tile-memory bandwidth saving on Apple GPUs), exposed as a capability string.
5. **Execution statistics + offscreen-present diagnostic + stage-boundary counter sampling** designs: valuable for honest benchmarking of Metallium (drawable acquire time, upload-ring blocked acquires, GPU span sums, resolve counters on completion, not via blit).
6. **3-slot upload ring with semaphore released in the completed handler** + transient arena retire-by-fence (`MetalTransientMemory`).
7. **Texture/sampler argument buffers + ICB path** as a design to reduce per-draw JNI/CPU: they show the problems (render-encoder split around compute for GPU ICB fill, need `useResource` for indirectly referenced index buffers, 16384 ICB limit, tracked hazards for ICBs, texture argument buffers need residency). Since it is default-off and un-benchmarked, treat as a map of pitfalls, not proof of benefit. Also CPU-side ICB population from published indirect snapshots.
8. **Shader-pack loader blueprint** (even though Metallium targets Iris itself): the legacy-GLSL lowering list (builtins -> `sl_*`, keyword escaping for Metal, DRAWBUFFERS parsing, hardware vs emulated shadow comparison with `sampler2DShadow`, comparison sampler `LEQUAL`), the explicit "reject, don't silently degrade" policy, and the unsupported-feature list are a good checklist for what an Iris-on-Metal path must cover (compute, setup passes, shadowcolor formats, size.buffer, image load/store). Relevant cross-check with notes/iris-shaders-translation.md.
9. **Scene-provider abstraction**: per-view `SceneSelection` with immutable generation, vanilla fallback provider, async index with "latest build wins" (`LatestIndexBuild`), event-driven dirty membership. The idea (selecting shadow-view sections from a spatial index while leaving camera occlusion to vanilla) is applicable if Metallium needs shadow pass terrain traversal without Sodium's own SectionRenderer.
10. Gametest harness: client gametest + screenshot assertions, per-pipeline SPIRV->MSL->Metal driver smoke test of *every* vanilla pipeline (cheap regression net for 26.x updates).

Things NOT to copy: hard-coded DeviceLimits/DeviceType.INTEGRATED, per-draw JNI + autoreleasepool + dynamic_cast, `Thread`-local one-shot hint scopes keyed on descriptor identity (fragile), weak pipeline-variant hash key, global single MTLFence serialization, exceptions-only error handling for lost GPU.
