## 0. TL;DR (decision-critical)

1. **Iris 26.3 is a hybrid that is hard-bound to the vanilla *OpenGL backend* (`renderpearl.backend.opengl`) — not to the API-neutral frontend.** [V]
   - It uses frontend APIs (`RenderSystem.getDevice().createTexture/createBuffer/createCommandEncoder().createRenderPass/clearDepthTexture`, `RenderPipeline`, `VertexFormat`, `GpuFormat`) for *some* allocation and for the vanilla draw path.
   - But all Iris-owned GPU work (gbuffer program objects, composite/deferred/final passes, compute, SSBOs, images, custom textures, colortex render targets, FBOs, uniforms, samplers, blend/depth overrides) is done with **raw LWJGL GL calls** (198 `GLxx.glFoo` call sites), **`GlStateManager._*` (236 call sites)** and its own wrapper **`IrisRenderSystem` (207 call sites; 879 LOC; DSA/ARB/legacy tiers)**.
   - Shader overriding works by **subclassing the GL backend's `GlProgram`** (`ExtendedShader extends GlProgram`, `pipeline/programs/ExtendedShader.java:51`) and **constructing new `GlRenderPipeline` backend objects** that are spliced into `FrontendRenderPipeline`s returned from `RenderSystem.getCompiledPipelineNullable` (`mixin/MixinShaderManager_Overrides.java:68-110`).
   - It relies on **GL global mutable state leaking into vanilla render passes**: after the GL backend binds a pipeline, Iris (`MixinGlRenderPipeline#iris$bind` → `ExtendedShader#iris$setupState`) re-binds its own FBO (`writingToBeforeTranslucent.bind()`), uploads loose `glUniform*`, binds textures/images, and overrides blend — inside a vanilla `RenderPass` whose attachments were fixed by vanilla. The shadow pass even **suppresses vanilla's `glBindFramebuffer`/`glDrawBuffers`/viewport in `GlCommandEncoder.createRenderPass`** (`mixin/MixinGlCommandEncoder.java:65-110`). This pattern is fundamentally impossible on explicit APIs (Metal/Vulkan render-pass attachments are fixed at encoder creation). [V]
2. **Iris checks the backend and refuses Vulkan.** [V] `mixin/IrisMixinPlugin.java:18-74`: a static initializer reads `<gameDir>/options.txt`, sets `usingVulkan = preferredGraphicsBackend.contains("vulkan")`, and `shouldApplyMixin` returns `!usingVulkan` for every mixin except ones whose class name contains `VKOnly` (only `VKOnly_InitKeys`). Iris's entry point is itself a mixin (`MixinOptions_Entrypoint`), so on Vulkan Iris never initializes; only a keybind + a placeholder screen "Iris cannot run when using Vulkan. Would you like to switch to OpenGL?" (`compat/sodium/config/ShaderPackScreenPlaceholder.java:30-45`) remain. In Sodium's video settings Iris overlays the `sodium:general.graphics_api` option with a confirm dialog "Setting the backend to Vulkan will remove your ability to use shaders" (`compat/sodium/config/IrisConfig.java:101-123`).
   - Caveat [SI/H]: the check is a *string match on the config value*, not on the actual device. If `preferredGraphicsBackend` is a default/auto value that resolves to Vulkan at runtime, Iris would apply all GL-backend mixins and then hard-cast `(GlDevice)` (`gl/IrisRenderSystem.java:579-581`) → ClassCastException. Values of `PreferredGraphicsApi` besides OPENGL/VULKAN are not visible in Iris. [U]
   - A Metal backend (Metallium) whose options value doesn't contain "vulkan" would therefore get **all GL mixins applied** to a non-GL device → crash on first `GlDevice` cast or on mixin targets (GlBackend etc. classes would still exist and mixins would apply but never run; casts would fail). [SI]
3. **No backend-agnostic abstraction or Vulkan/Metal work exists in Iris.** [V] Only seams: (a) `IrisRenderSystem` static facade (GL-shaped signatures: int GL names/enums), (b) `IrisLimits.VK_CONFORMANCE = false` gating `LayoutTransformer` (explicit `layout(location=)` assignment for in/out varyings; `gl/IrisLimits.java:14`, `pipeline/transform/TransformPatcher.java:218-220`) — the only Vulkan-oriented code, disabled at compile time, (c) `WorldRenderingPipeline` interface (`pipeline/WorldRenderingPipeline.java`) with `VanillaRenderingPipeline` and `IrisRenderingPipeline` implementations, (d) `IrisApi` (`common/src/api`, 316 LOC). Remote branches (`UBO-proper` 2022, `feature/gl4UBO` 2023, `future` 2024…) contain no Vulkan work by name; commit-message grep for "vulkan" returns nothing. [V for names/messages; branch contents not audited]
4. **Sizes** (common/src/main/java, 59,329 LOC Java total; fabric+neoforge 653 LOC): files with direct GL coupling (lwjgl.opengl / backend.opengl / GlStateManager / IrisRenderSystem / glId): **145 files, 20,261 LOC**; files touching only renderpearl/blaze3d frontend: **95 files, 9,158 LOC**; files with no graphics-API reference: **452 files, 29,804 LOC** (includes glsl-transformer patcher 3.8k, stareval expression engine 2.6k, shaderpack parsing/options ~7k, gui, culling). See §14.
5. **macOS today**: Iris on macOS runs on GL 4.1, so `FeatureFlags` COMPUTE_SHADERS, SSBO, CUSTOM_IMAGES (image load/store), TESSELLATION (4.0 ok), PER_BUFFER_BLENDING (4.0 ok) gate packs; compute/SSBO/images unavailable on mac GL 4.1 [SI from capability checks `gl/IrisRenderSystem.java:299-305,74`]. Iris has a dedicated lang string `iris.unsupported.pack.macos`: "macOS is known to have issues with many shader packs." (`shaderpack/ShaderPack.java:231-233`). A Metal path would be the first way to give mac users compute/SSBO/image packs.

## 18. Approaches for Metallium

### A. Adapt Iris (fork/patch to run on a Metal backend)
Must touch: (1) `IrisMixinPlugin` backend detection (treat Metal as supported; gate GL-backend mixins); (2) replace `IrisRenderSystem` + `gl/*` with a backend interface (textures, samplers, FBO→render pass descriptors, programs→Metal pipelines, uniform blocks, SSBOs, images, compute, barriers) — ~6k LOC + ~3k call sites in pipeline/targets/shadows; (3) re-architect gbuffer integration: today Iris rebinds FBOs/uniforms *inside* vanilla GL render passes; on Metal the Iris colortex attachments must be chosen when the vanilla `RenderPass` is created → needs hooks in the *frontend* (`CommandEncoder.createRenderPass`) or Metallium's backend to redirect attachments per phase; program override must create Metallium backend pipelines instead of `GlRenderPipeline` (`MixinShaderManager_Overrides`); (4) uniform model: loose `glUniform*` → per-draw uniform buffer/argument buffer layout derived from shader reflection (SPIRV-Cross); (5) GLSL → MSL path (glsl-transformer output → glslang → SPIR-V → SPIRV-Cross MSL), enable `LayoutTransformer` (VK_CONFORMANCE) for explicit locations; (6) composite/final draw loops → Metal render encoders; compute → compute encoders + explicit barriers/fences instead of `glMemoryBarrier`; (7) per-buffer blending and mixed-format MRT limits (Metal: 8 color attachments vs Iris MAX 32 / packs typically ≤16 — **hard limit concern** [SI]); (8) StandardMacros GL version/vendor/extension emulation; (9) DH unsupported unless DH runs on Metal; (10) license: LGPL-3.0 + AGPL glsl-transformer. Effort: touching ≈20k GL-bound LOC + parts of 9k frontend LOC; keeps ~30k neutral LOC. Upstream churn per MC version is high (Iris 26.x mixes frontend/backends weekly).
### B. Reimplement (clean-room Iris-compatible pipeline natively on Metal)
Reimplement: pack loader/options/properties/directives/ID maps (~10-12k LOC equivalent, spec = OptiFine `shaders.txt` docs + Iris behavior), custom uniform expression language (~2.6k), uniform providers (~3.5k), program fallback/selection, pass scheduler, render targets/flip/clear/mipmap semantics, shadow pass via Sodium shadow render lists (needs equivalent Sodium mixins ~1.6k), extended vertex formats, entity ID capture (~1.2k mixins), GLSL patching (the hardest: 4.8k LOC of transformer logic encodes many compat quirks) → GLSL→SPIR-V→MSL. Avoids LGPL/AGPL code reuse; most work; behaviorally divergent from Iris unless carefully matched.
### C. Translation layer (run Iris unmodified on a GL-over-Metal shim)
Implement the subset of GL 4.5 Iris + vanilla GL backend + Sodium use (inventory §14; incl. DSA, multibind, SSBO, image load/store, compute, KHR_debug, ARB_draw_buffers_blend, texture swizzle, copyImageSubData, clear_texture, tessellation `GL_PATCHES`) on Metal (à la MoltenGL/ANGLE-Metal/Zink-like). Requires: GL context emulation under SDL (`MixinWindow` targets `GlBackend.createWindow` SDL GL attributes), GLSL 1.20–4.60 compiler front-end (glslang) → MSL, emulation of geometry/tessellation shaders (Metal has no GS; tessellation model differs), global-state → encoder translation with render-pass splitting on every FBO rebind (Iris rebinds per draw), `glMemoryBarrier` mapping, 8-attachment limit. Iris and vanilla GL backend would run unchanged (and `IrisMixinPlugin` sees "opengl"); performance is the main risk (state-tracking overhead, pass splitting), plus correctness of GL semantics. Size of GL surface: ~120 distinct GL entry points used by Iris itself (§14) + whatever vanilla `renderpearl.backend.opengl` and Sodium use [U].
