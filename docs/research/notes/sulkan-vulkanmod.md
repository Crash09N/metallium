## PART A. SULKAN
======================================================================

### A0. TL;DR (decision-relevant)
1. **Sulkan is NOT a gbuffer/Iris-style pipeline.** It is a fixed set of hand-written effects (shadow cascades, SSAO, SSR-ish water, volumetric clouds, atmosphere shafts, bloom, FXAA) built ONLY from vanilla `RenderPipeline` / `CommandEncoder.createRenderPass` / `RenderTarget` calls plus mixins. Zero raw Vulkan: the only `org.lwjgl.*` it touches is **shaderc** (Verified: `grep -rn lwjgl|vulkan` over all sulkan java hits only NativeShaderCompiler + the VulkanDevice mixin). No compute, no SSBO, no loose uniforms, no compare samplers, no storage images, no push-constant authoring of its own (Verified: no `image2D|buffer|compute|imageLoad` in its GLSL; only `layout(push_constant)` block in sodium_terrain_*.vsh copied from Sodium's VULKAN branch).
2. **It cannot load Iris/OptiFine packs.** "Shader pack" = a zip/dir containing `assets/sulkan/shaders/**` (or `shaders/**` remapped to it); it is expanded into a generated *resource pack* `resourcepacks/sulkan_shaderpack_active` that overrides the mod's built-in `.fsh/.vsh/.glsl` files. It can restyle existing passes, it cannot add passes/targets (pass list is hard-coded in Java). Verified: `sulkan/pack/ShaderPackScanner.java:L70-L87` (mapEntry), `:L96-L99` (unsupported reason "missing-assets-sulkan-shaders"), `sulkan/pack/ShaderPackRepository.java:L69-L80` (rebuildGeneratedPack), `:L130-L143` (pack.mcmeta), `:L52-L61`.
3. **Stale vs our target.** Repo pinned to MC 26.2 (`gradle.properties`: minecraft_version=26.2, sodium 0.9.1+mc26.2, fabric 0.155.0; fabric.mod.json `minecraft ~26.2`). Its mixin targets are 26.2 class names `com.mojang.blaze3d.vulkan.{VulkanDevice,VulkanRenderPipeline,VulkanBindGroupLayout,glsl.GlslCompiler,glsl.IntermediaryShaderModule}`, `com.mojang.blaze3d.{pipeline.RenderPipeline,systems.RenderPass,...}`. In 26.3 these moved to `com.mojang.renderpearl.*` (`mc26.3/com/mojang/renderpearl/{api,frontend,backend/vulkan}`; `com/mojang/blaze3d/vulkan` does NOT exist; `getOrCompilePipeline` does not exist anywhere in mc26.3: grep empty). So the central hook (A2) is dead on 26.3 and must be re-done against `FrontendGpuDevice/PipelineBuilder`. Repo has 6 commits total (2026-05-09..2026-08-20). The task says Modrinth has v0.6.0 for 26.3: Unverified (no network to Modrinth; repo at v0.3.1 so the 26.3 port is closed/unpublished source).
4. **Runs over MoltenVK on macOS (relevant!).** Comment in `NativeShaderCompiler.java:L31-L35`: "Optimizing those modules first can change packed Sodium input types or compact conditional entity varyings incompatibly on MoltenVK." => author tests on Mac/MoltenVK; confirms vanilla Vulkan backend + Sodium + custom pipelines is viable on MoltenVK (Strongly inferred; no direct runtime evidence).
5. **Key lesson for Iris-on-Metal "attachments fixed at pass creation":** Sulkan sidesteps it entirely. Each pass = one color attachment (+ optional depth); pipelines declare their `ColorTargetState(format)` and `DepthStencilState`; separate pipeline objects per variant (caster vs receiver, per terrain layer, per quality tier via `withShaderDefine`) are cached in IdentityHashMaps. No MRT use at all. Note vanilla 26.3 DOES support MRT: `ColorTargetState.MAX_COLOR_TARGETS = 8` (`mc26.3/com/mojang/renderpearl/api/pipeline/ColorTargetState.java`) and `RenderPassDescriptor` with a list of color attachments; VulkanCommandEncoder uses dynamic rendering (`backend/vulkan/VulkanCommandEncoder.java:L351-L375`, `vkCmdBeginRenderingKHR`). So for Iris gbuffers the SPI already has what is needed; Sulkan does not exercise it.
6. **Licence:** GPL-3.0-only (`fabric.mod.json "license":"GPL-3.0-only"`, README, LICENSE). Any copied code would force Metallium to GPL-3.0. Ideas only.

### A1. Architecture & lifecycle
- Entry: `SulkanShadersClient#onInitializeClient` (`SulkanShadersClient.java:L12-L18`): `ShaderRuntime.init()`, bootstrap on CLIENT_STARTED, `ShaderRuntime.close()` on CLIENT_STOPPING. Verified.
- `ShaderRuntime` (`runtime/ShaderRuntime.java`) holds config, pack list, `ShaderPipelineState` (booleans: shadows/ao/water/clouds/atmosphere/bloom/fxaa; `runtime/ShaderPipelineState.java:L5-L35`). `applyConfig` (L88-L117) toggles pipelines then, if the selected pack changed, calls `minecraft.reloadResourcePacks()` (full resource reload = vanilla `ShaderManager` re-reads shaders) and `invalidateTerrainRenderer` -> `levelRenderer.invalidateCompiledGeometry` (L186-L194). So shader change == resource reload; no hot incremental recompile. Verified.
- Mixin list (`resources/sulkan-shaders.mixins.json`): CloudRenderer, LevelRendererPost, LevelRendererShadow, OptionsScreen, RenderPipelinesAccessor, RenderType(PreparedRenderType), SkyRenderer, SubmitNodeStorage, VulkanDeviceShaderCompiler, and 7 Sodium mixins (DefaultChunkRenderer, RenderRegion, RenderSectionManagerAccessor, ShaderChunkRenderer, SodiumWorldRendererAccessor/Mixin, TerrainRenderPass). `required:true, defaultRequire:1`. No backend check anywhere (grep "vulkan|backend|isMac" in non-mixin code: empty), so on a GL backend the VulkanDevice mixin is simply never loaded/used while the other pipelines would still be built (Hypothesis: shaders would be GL-compiled via vanilla path; not tested).

### A2. How it hooks vanilla's Vulkan backend
Mixin on `VulkanDevice` (26.2) `@Inject(getOrCompilePipeline, HEAD, cancellable)` `mixin/VulkanDeviceShaderCompilerMixin.java:L31-L65`:
- Only intercepts pipelines whose VS or FS identifier namespace is `sulkan` (L50-L53); everything else goes through vanilla untouched.
- Re-implements the compile path: fetch GLSL via `defaultShaderSource.get`, then `ShaderManager.getShader`, then classpath fallback with its own `#moj_import` include resolver (L91-L138); inject `#define`s with `GlslPreprocessor.injectDefines` (L76-L79); call **its own shaderc** (`NativeShaderCompiler`) to produce `IntermediaryShaderModule.createFromSpirv` (L81-L82); then hand to vanilla `glslCompiler.compile(device, pipeline, vertexModule, fragmentModule)` and `VulkanRenderPipeline.compile(...)` (L83-L84) i.e. reflection/binding rewrite/pipeline creation remain vanilla; result cached in vanilla's `pipelineCache` (L55-L63). On failure returns a dummy `VulkanRenderPipeline(... handles 0 ..., INVALID_LAYOUT)` (L157-L160).
- WHY it needs its own shaderc: Sulkan shaders are `#version 450/460 core` Vulkan-dialect GLSL (e.g. `sodium_terrain_receiver.vsh:L1-L11` uses `layout(binding=N)`, `#ifdef VULKAN layout(push_constant)`, `isamplerBuffer`), not vanilla's `#version 330`-with-auto-binding dialect; and it wants `target_env vulkan1.3`, `preserve_bindings`, `-O` performance (`NativeShaderCompiler.java:L19-L28`). Optimization level forced to 0 for `entity_shadow_` and `sodium_terrain_` shaders (L36-L39, L61-L63) because vanilla rewrites vertex-input/inter-stage locations *after* reflection.
- **Lesson for Metallium:** vanilla's shader frontend (26.3: `frontend/shaders/PipelineBuilder`, `GlslCompiler`) already produces SPIR-V; a Metal backend gets `SpvModule`. The equivalent Sulkan hook point in 26.3 is the frontend `compilePipeline(pipeline, shaderSource, executor)` (`mc26.3/.../FrontendGpuDevice.java:L206-L208` -> `PipelineBuilder.compilePipeline` `:L375-L390`) or simply a custom `ShaderSource` (`api/pipeline/ShaderSource.java`) that returns Sulkan/Iris-translated GLSL; no backend change needed for pure GLSL supply. Hypothesis: for Iris, supplying GLSL through `ShaderSource` + `RenderPipeline.withShaderDefine` + `BindGroupLayout` is enough as long as the shader fits the UBO/sampler/texel-buffer-only resource model (see vanilla-renderpearl.md TL;DR 4).

### A3. How passes and targets are added
**Post chain (screen-space)** - `mixin/LevelRendererPostMixin.java`:
- `@Inject(LevelRenderer#render, HEAD)` L46-L78: per-frame prepare (cloud/atmosphere uniforms, `WaterSceneCapture.beginFrame`).
- `@Inject(LevelRenderer#render, RETURN)` L80-L181: builds a pass list (water, AO, clouds, atmosphere, bloom, FXAA), ping-pongs between two RGBA8 scratch targets via `PostChain` (`render/PostChain.java:L225-L245`: `begin` copies main color -> targetA with `copyTextureToTexture`; `output()` returns main target for the LAST pass else the other scratch target; `copyToMain` if needed), `encoder.submit()` in `finally` (L178-L180). Everything runs AFTER vanilla's whole level render (so after translucency, particles, weather, and with GUI not yet drawn). It creates its own `CommandEncoder` (`RenderSystem.getDevice().createCommandEncoder()` L128) rather than joining the FrameGraph. Verified.
- Each effect: `FullscreenPostRenderer` (`render/FullscreenPostRenderer.java`) `encoder.createRenderPass(label, colorView, Optional.empty(), null, OptionalDouble.empty())` -> `setPipeline` -> `RenderSystem.bindDefaultUniforms` -> `bindTexture(name, view, sampler)` -> `setUniform(name, slice)` -> `draw(3,1,0,0)` (fullscreen triangle) e.g. L58-L69. Single color attachment, no depth attachment, no scissor/viewport calls.
- Pipelines: `runtime/ShaderPipelines.java:L57-L68` builds `RenderPipeline.builder(RenderPipelines.POST_PROCESSING_SNIPPET).withBindGroupLayout(BindGroupLayout.builder().withSampler(..).withUniform("SulkanSceneParams", UniformType.UNIFORM_BUFFER).build())`. All resources are named samplers + std140 UBOs (the vanilla model). Depth is sampled as a normal `sampler2D` with NEAREST (FullscreenPostRenderer L66, `bindTexture("SceneDepthSampler", depthSource.getDepthTextureView(), nearestSampler)`).
- Render targets: `render/ShaderRenderTargets.java:L193-L204` -> `RenderTargetDescriptor(w,h,useDepth,clear,GpuFormat.RGBA8_UNORM)`; always RGBA8 (no HDR/RGBA16F intermediate; bloom/tonemap are done in LDR - quality limitation). Half/quarter-res AO and water targets re-allocated on resize (`FullscreenPostRenderer.ensureAoTarget/ensureWaterTarget` L177-L203).
**Shadow pass (geometry)** - `mixin/LevelRendererShadowMixin.java`:
- `@Inject(LevelRenderer#addMainPass, HEAD)` L126-L194 adds a FrameGraph `FramePass "sulkan:directional_shadow_maps"` with `disableCulling()` and an `executes` lambda that loops 4 cascades; each: upload cascade UBO (`encoder.writeToBuffer`), `clearColorAndDepthTextures`, then render Sodium terrain with swapped pipelines (below) and entity submits through a *second* `FeatureRenderDispatcher`/`RenderBuffers` pair (L247-L258) so that a clean "shadow frame" of entity submits can be executed (L227-L244). Entity submits are captured by an extra `@Inject` before `submitFeatures` (L88-L124) using a `DirectionalShadowSubmitFilter` collector + near/far `SubmitNodeStorage`s, with `levelRenderState.shouldShowEntityOutlines` temporarily forced false (L114-L123).
- Shadow maps: `RenderTargetDescriptor(size,size,true,CLEAR,GpuFormat.R8_UNORM)` (`render/shadow/DirectionalShadowRenderer.java:L427,L433`): an R8 color + a real depth attachment per cascade (4 terrain + up to 4 entity targets); the receiver samples the **depth** view with NEAREST and does manual PCF/bilinear compare (`include/directional_shadow.glsl:L93-L94,L144-L145`: `step(compareDepths, depths)`), i.e. **no hardware comparison sampler** (workaround for the API gap). Update rate throttling: cascade update intervals {3,8,16,32} frames, entity {1,2,4,8}, plus movement/light-direction thresholds (`DirectionalShadowRenderer.java:L29-L31`, `shouldUpdateCascade`) and cached per-cascade Sodium render-lists (see A5). Good performance idea (temporal shadow cascade amortisation) independent of API.
- Entity casters/receivers: `mixin/RenderTypeMixin.java` on `PreparedRenderType#drawFromBuffer` - cancels the vanilla draw when `isRenderingShadowMap()` and issues its own render pass into the active cascade (L34-L91, one `createRenderPass` PER DRAW - expensive but simple), and `@Redirect setPipeline/bindTexture` to swap in receiver pipelines (`ENTITY_SOLID/CUTOUT/TRANSLUCENT` identity-compared with `RenderPipelines.*` L129-L146) and bind shadow maps/UBO (L93-L127). `SubmitNodeStorageMixin` cancels vanilla blob shadows (L171-L180). `RenderPipelinesAccessor` exposes `ENTITY_SNIPPET` to derive pipelines.
- Water: `mixin/sodium/SodiumWorldRendererMixin.java:L18-L33` injects at HEAD of Sodium's `drawChunkLayer` for `TRANSLUCENT` group and copies main color+depth into `WaterSceneCapture` (`render/water/WaterSceneCapture.java:L473-L477`: two `copyTextureToTexture` + extra `encoder.submit()`), later consumed by the SSR-like water trace/composite passes. So "gbuffer-ish" data = a pre-translucent colour+depth copy, not MRT.
- Clouds/sky: `CloudRendererMixin` cancels vanilla `CloudRenderer#render` and requests a volumetric trace executed in the post chain; `SkyRendererMixin` re-orients/scales sun/moon (`@ModifyConstant 30.0f/20.0f`).
**What it does NOT have:** no deferred gbuffers (albedo/normal/material), no composite chain driven by pack metadata, no custom `RenderPass` ordering API; all passes are Java-coded.

### A5. Sodium integration (Sodium 0.9.1 on renderpearl-era API)
Important: this shows Sodium 0.9.x terrain is already `RenderPipeline`-based and pluggable, no raw GL.
- `ShaderChunkRendererMixin` (`mixin/sodium/ShaderChunkRendererMixin.java:L23-L35`): `@Inject compileProgram(TerrainRenderPass) HEAD cancellable` returns Sulkan caster pipeline when `DirectionalShadowRenderer.isRenderingShadowMap()` (ThreadLocal flag), else the receiver pipeline (`SodiumTerrainShadowPipelines.receiver(pass, this.vertexFormat)`). I.e. **terrain "shader replacement" = replace the `RenderPipeline` Sodium asks for** (Sodium caches/derives from `TerrainRenderPass`). - `DefaultChunkRendererMixin` (`:L21-L53`) `@Redirect` on the 2nd `RenderPass#bindTexture` inside `DefaultChunkRenderer#render` to additionally bind `SulkanShadowData` and 8 shadow samplers into Sodium's own render pass (extra resources piggy-backed onto Sodium's pass, no new pass).
- `RenderRegionMixin` (`:L29-L37` getStorage/getCachedBatch, plus invalidation hooks) gives each shadow pass its own cached `MultiDrawBatch` per region while sharing the source mesh storage (`SodiumShadowTerrainPasses`), and bumps a `shadowRevision` on `setSectionRenderState/clearSectionRenderState` so cached light-space render lists are rebuilt only when geometry changed.
- `SodiumShadowTerrainRenderer.renderCascade` (`render/shadow/SodiumShadowTerrainRenderer.java:L166-L203`): builds light-space `ChunkRenderList`s per region from section/cascade AABB test, **temporarily flips Sodium's global option `useBlockFaceCulling=false`** (L63-L73 in the file; hack, not thread-safe), calls `sectionManager.getChunkRenderer().render(...)` directly with its own `ChunkRenderMatrices` and `FogParameters.NONE`, reusing Sodium's `UniformBufferManager` via accessor mixins (`SodiumWorldRendererAccessor`).
- Hard dependency: Sulkan REQUIRES Sodium (`fabric.mod.json depends sodium>=0.9.1`); vanilla terrain path is not handled.
- Lesson: for Metallium, a Sodium that targets renderpearl `RenderPipeline` (0.9.x) lets an Iris adapter swap terrain pipelines at `compileProgram` (this is exactly how Iris-for-Sodium works on GL too; cross-check iris-arch.md). The rewritten pipelines must keep Sodium's vertex input layout (`USE_VERTEX_COMPRESSION`), `u_Globals`, `u_SectionTimeInfo` texel buffer, and the push-constant region block.

### A6. Shader authoring/compile
- Authoring: GLSL 450/460 `.fsh/.vsh/.glsl` under `assets/sulkan/shaders/{core,include}`; includes via vanilla `#moj_import <sulkan:...>` (own resolver, mixin L119-L138). Resource build strips comments/blank lines (`build.gradle` processResources doLast).
- Compile: runtime, per pipeline, on first use (`getOrCompilePipeline` hook): shaderc -> SPIR-V (vulkan1.3, auto_bind_uniforms, auto_map_locations, preserve_bindings, debug info, -O performance except Sodium/entity) -> vanilla reflection/rewrite. No disk cache of SPIR-V/pipelines seen (Unverified for pipeline cache inside vanilla). Compile happens synchronously on the render thread inside the hook (no `executor` use) - stalls possible on first use of each variant.
- Metal-relevance: shader sources already pass through SPIR-V; they would then need SPIRV-Cross MSL (Metallum has `MetalCrossShaderCompiler`, see metallum.md). Sulkan GLSL uses `isamplerBuffer`, `texelFetch`, UBO arrays of struct, `layout(early_fragment_tests)`-like features? (not checked) - no features outside the vanilla-supported subset except the push-constant block (allowed, <=128 B).

### A7. Uniform model
- Per-effect std140 UBOs sized by constants (`ScenePostUniforms.PARAM_BYTES = 64+64+16*4+64+16+16*4`, `render/ScenePostUniforms.java:L26`), CPU-assembled each frame in a direct `ByteBuffer`, uploaded with `encoder.writeToBuffer(slice, buf)`. Camera/sun/fog/time derived from `CameraRenderState`, `LevelRenderState.skyRenderState`, `Minecraft.level` (L63-L149). No "Iris uniform provider" abstraction: ~40 fields hard-wired. Custom sun orbit (`CustomCelestials`, yaw -45 deg) affects lighting vs vanilla sky (mixin keeps visuals consistent).

### A8. Attachment/pass model & the "fixed at render-pass creation" problem
- Sulkan never changes attachments within a pass. Different attachment sets = different `createRenderPass` calls = different pipelines (formats baked into `ColorTargetState`). Per-draw render pass creation in entity-shadow path (`RenderTypeMixin.java:L68-L89`) means one pass per entity draw: costs nothing special on Vulkan dynamic rendering but on Metal each pass = encoder begin/end (tile load/store flush on TBDR). **Avoid for Metal**: batch into one pass per cascade (Hypothesis: Sulkan's approach would be slow on Apple GPUs).
- Vanilla 26.3 VulkanCommandEncoder issues a global `VkMemoryBarrier2` (stage 65536 = ALL_GRAPHICS? / access 98304) after every `submitRenderPass` (`backend/vulkan/VulkanCommandEncoder.java:L253-L262,L411`) so Sulkan needs ZERO explicit barriers/layout transitions; no image layout tracking (dynamic rendering + implicit barrier). Also each `encoder.submit()` = full queue submit + wait on submit N-2 (`:L264-L281`); Sulkan calls `createCommandEncoder().submit()` several times per frame (shadow pass, water capture, post chain) - extra submits, cost on Vulkan; on Metal this is `commit` per submit (Hypothesis: cheap-ish but breaks command-buffer batching; a Metal backend should make `submit()` cheap/aliasable).
- Implication for Metallium Iris adapter: pipelines+render passes are described by *formats at pipeline creation* (`ColorTargetState.format`, up to 8) and *attachments at pass creation* (`RenderPassDescriptor`); mapping to MTLRenderPipelineDescriptor/MTLRenderPassDescriptor is 1:1, so an Iris "drawbuffers" set becomes (a) a family of `RenderPipeline`s keyed by the attachment-format tuple, (b) `RenderPassDescriptor` with N colour attachments. Sulkan shows the cache-by-IdentityHashMap-per-variant pattern but not MRT.

### A9. Sync/barriers
- None of its own (see A8). Ordering relies on vanilla's per-pass global barrier + sequential submit. `WaterSceneCapture.captureFrom` mid-frame copy then `encoder.submit()` (L473-L477) forces a submit boundary inside Sodium's translucent pass setup (Strongly inferred: this ends any in-flight pass? Not verified whether a pass is open; it is invoked at `drawChunkLayer` HEAD, before Sodium opens its pass).

### A10. Limitations / bugs / risks (Sulkan)
- Pinned to 26.2 internals; broken on 26.3 (A0.3).
- Requires Sodium; mutates Sodium global option at runtime (A5); relies on ThreadLocal "isRenderingShadowMap" flags and `Overwrite`-style cancels - fragile vs other mods (Iris would conflict; no compat code).
- Post effects after entire level render: bloom/FXAA/AO operate on LDR RGBA8; HUD/hand ordering effects undefined; translucents not in depth for AO.
- Duplicate entity/terrain geometry submissions for shadows (entities re-submitted; 4 cascades; throttled).
- Compile on render thread; resource reload on every pack/setting change.
- `resourceReloading()` guards everywhere (static volatile) - reload race handled by early-outs.
- `sulkan$invalidPipeline` returns pipeline with handle 0 on failure: would crash when bound (Hypothesis).
- Nothing on GL backend: no backend gating (A1).
- Licence: GPL-3.0 (copy => GPL for Metallium). Ideas only: temporal cascade scheduling, per-region cached light-space batches, pipeline-swap-at-compileProgram, manual PCF on depth, half-res AO/water traces.

Note: source mod version `0.6.8+1.21.11-dev` (gradle.properties); lwjgl 3.3.3 (`build.gradle:L43`), bundles lwjgl-vulkan, vma, shaderc, spvc natives incl. macOS (L51-L67). Licence LGPL-3.0 (task; `LICENSE` file present, not re-read). 26.1 releases are not in the repo (Unverified).

### B0. TL;DR
1. **Not on the renderpearl SPI.** 1.21.11 era: VulkanMod replaces the GL stack: `@Overwrite`/redirect mixins on `GlStateManager`, `RenderSystem`, `GL11/14/15/30` (`resources/vulkanmod.mixins.json` lists `compatibility.gl.GL11M…GL30M`, `render.GlStateManagerM`, `render.RenderSystemMixin`), a GL-emulation layer (`vmod/gl/VkGl*`), and also implements vanilla's 1.21.11 `GpuDevice` as `render/engine/VkGpuDevice implements GpuDevice` (L42) with `VkCommandEncoder/VkRenderPass/VkGpuBuffer/VkGpuTexture`. So it is a "blaze3d-level" Vulkan backend where available, GL-shim elsewhere. For 26.x the renderpearl SPI replaces this need (vanilla ships its own VulkanBackend).
2. **Terrain renderer is the valuable part** (own chunk system, replaces vanilla `LevelRenderer` chunk mixins `chunk.LevelRendererMixin`, `ViewAreaM`, `SectionRenderDispatcherM`, …). Techniques transferable to Metal listed in B7.
3. **Sodium/Iris: no compatibility.** `grep -rli sodium|iris|embeddium` in src: only a code comment in `SmoothLightPipeline.java` (lighting code is ported/adapted from Sodium-like approach; licence provenance Unverified). VulkanMod is itself a Fabric renderer provider: `fabric.mod.json custom "fabric-renderer-api-v1:contains_renderer": true` and has its own FRAPI implementation (`render/chunk/build/frapi/**`, mixins `render.frapi.*`). Shaders: README points to closed-source "Beryl" (Modrinth) - Unverified/closed; nothing in repo.
4. **Vulkan features:** dynamic rendering ON (`Vulkan.DYNAMIC_RENDERING = true`, `vulkan/Vulkan.java:L51`; legacy VkRenderPass path kept behind flag `vulkan/framebuffer/RenderPass.java:L36-L38,createRenderPass`), VMA for all memory, push constants for per-area origin, indirect multi-draw, separate transfer queue for uploads. Single colour attachment (+depth) per pass (`RenderPass(framebuffer, colorAttachmentInfo, depthAttachmentInfo)`); no MRT.

### B1. Architecture
- Entry `net.vulkanmod.Initializer` (fabric.mod.json); `Vulkan.java` (499 lines) instance/device/VMA; `Renderer.java` (894) frame loop; `Drawer` draw helpers; `VRenderSystem` GL-state mirror.
- GL emulation: mixins on LWJGL GL classes (`mixin/compatibility/gl/GL11M, GL14M, GL15M, GL30M`) + `gl/VkGl*` classes translate GL calls (textures, framebuffers) to Vulkan objects (`gl/VkGlFramebuffer.java:L234` etc.), to keep vanilla code (written against GlStateManager) working. Vanilla pipelines (`RenderPipeline`) are converted by `render.shader.RenderPipelineM` + own `PipelineManager/CustomRenderPipelines` into VulkanMod `GraphicsPipeline`s (`render/shader/*`).
- 1.21.11 `GpuDevice` implementation: `render/engine/VkGpuDevice.java` (pipelineCache `IdentityHashMap<RenderPipeline,…>` at L57; inner `VkRenderPipeline implements CompiledRenderPipeline` L422).

### B2. Frame loop, sync, frames in flight
- `Renderer.framesNum = CONFIG.frameQueueSize` (default **2**, `config/Config.java:L27`; `Renderer.java:L110`).
- Per-frame resources: one primary cmd buffer per frame (L143-L160), transfer cmd buffers (L171-L173), `imageAvailableSemaphores` per frame, `inFlightFences` per frame (created signaled), **`renderFinishedSemaphores` per swapchain image** (L179-L217; comment: presentation-engine signal only guaranteed by acquire).
- `beginFrame` (L238-L): `vkWaitForFences(inFlightFences[currentFrame])` (L251) -> submit pending uploads -> `MemoryManager.initFrame(currentFrame)` (frees deferred resources) -> staging buffer `beginFrame` -> reset cmd buffer -> `vkAcquireNextImageKHR` -> begin main pass. `endFrame`/`submitFrame` (L324-L420): single `vkQueueSubmit` waiting on upload semaphores (TOP_OF_PIPE) + imageAvailable (COLOR_ATTACHMENT_OUTPUT), signalling renderFinished[imageIndex], fence; then `vkQueuePresentKHR`. `flushCmds` (L425-L470) = mid-frame full submit+wait for readbacks (screenshots).
- Deferred destruction: `AreaBuffer.freeSegment` -> `MemoryManager.addToFreeSegment` ("delay segment freeing since it might still be used by prev frames in flight", `AreaBuffer.java` comment); `MemoryManager.addFrameOp` for framebuffer destruction (`Framebuffer.cleanUp`).
- Present mode: vsync -> FIFO; uncapped -> IMMEDIATE else MAILBOX, fallback FIFO (`SwapChain.java:L34,L251-L264`).
- Metal mapping: fence-per-frame = `dispatch_semaphore`/`MTLSharedEvent` with 2-3 frames in flight (CAMetalLayer `maximumDrawableCount` 2-3); deferred segment free = ring of "retire after frame N" lists. (Strongly inferred)

### B3. Memory
- **VMA** (lwjgl-vma): `vmaCreateBuffer/vmaCreateImage` (`vulkan/memory/MemoryManager.java:L116-L181`), budget polling `vmaGetHeapBudgets` (L326-L332) for VRAM stats. Own memory-type classification (`MemoryTypes.java:L16-L58`): GPU_MEM = DEVICE_LOCAL (prefers DEVICE_LOCAL|HOST_VISIBLE "DeviceMappableMemory" i.e. ReBAR/UMA when found, L44-L47), HOST_MEM = HOST_VISIBLE|COHERENT; fallback GPU_MEM=HOST_MEM (L58).
- Staging: per-frame `StagingBuffer` ring (`memory/buffer/StagingBuffer(s).java`), uploads recorded on a **dedicated transfer queue** command buffer (`render/chunk/buffer/UploadManager.java:L24-L66`: `DeviceManager.getTransferQueue()`, `recordUpload` copies into staging then `vkCmdCopyBuffer`, barrier only on WAW to same buffer, `submitUploads` signals semaphore consumed by next graphics submit - `Synchronization.INSTANCE`).
- Metal mapping: on Apple Silicon UMA all `MTLStorageModeShared` buffers are CPU-writable and GPU-visible: staging+transfer queue is unnecessary; write directly into persistently mapped shared buffers guarded by per-frame ring/`MTLFence`/event. Keep the suballocator design (AreaBuffer) but upload with `memcpy` (+ `didModifyRange` N/A on shared). (Hypothesis, standard Apple guidance.)

### B4. Terrain renderer (the core)
Data structures:
- `ChunkAreaManager` (`render/chunk/ChunkAreaManager.java`): areas of 8x8(x8 high) sections = `AREA_SIZE = WIDTH*WIDTH*HEIGHT = 512` (L12-L15). Each `ChunkArea` owns a `DrawBuffers` (`render/chunk/buffer/DrawBuffers.java`). This is comparable to Sodium's RenderRegion (8x4x8=256 there).
- `DrawBuffers`: per terrain render type (SOLID, CUTOUT, TRANSLUCENT, TRIPWIRE; `TerrainRenderType`) one **AreaBuffer** = a big GPU vertex buffer with a first/best-fit free-list sub-allocator (`AreaBuffer.java`: `findSegment` best fit L~140, `allocateSegment`, `freeSegment` deferred, `upload(segment,…)` records a staged copy) with initial sizes SOLID 100000 / CUTOUT 250000 / TRANSLUCENT 60000 elements (`DrawBuffers.java:getAreaBufferOrAlloc`), growth by reallocation (not read in detail). Separate lazily created index AreaBuffer (60000 shorts) only for sections with custom indices (translucent sorting); otherwise a shared global quad index buffer (`Renderer.getDrawer().getQuadsIndexBuffer()`).
- **Per-section, per-facing draw params** in native memory (`DrawParametersBuffer`: indexCount/firstIndex/vertexOffset/baseInstance, STRIDE x 7 facings x 512 sections x renderTypes). Vertices of a section are stored contiguously **sorted by quad facing** (QuadFacing.COUNT, UNDEFINED last) so face culling = pick a subset (`DrawBuffers.upload` L~60-L140).
- **Compressed terrain vertex: 16 B** = 4 x int16 position (+offset POS_OFFSET 4.0) + 2 x uint16 UV + uint32 colour (`render/vertex/CustomVertexFormat.java:L7-L18`); light packed in colour/UV (vertex shader decodes; `shaders/basic/terrain`). Section origin recovered in shader from per-area push constant + `baseInstance`/draw-id-indexed UBO `SectionData` (4096 B, `PipelineConfigs.TERRAIN_UB2`, section offsets 3x7bit packed `encodeSectionOffset` in `DrawBuffers.java`, fade-in floats appended at +512*4).
Draw submission (`WorldRenderer#renderSectionLayer`, `WorldRenderer.java:L326-L433`):
- Set pipeline once per layer; iterate visible **areas** (`sectionGraph.getChunkAreaQueue()`, near-to-far; translucent reverse), per area: `drawBuffers.bindBuffers` (bind vertex/index buffers, push area origin via `vkCmdPushConstants` `DrawBuffers.updateChunkAreaOrigin`, update section UBO), then `buildDrawBatchesIndirect` or `…Direct` depending on `CONFIG.indirectDraw` (default true, `Config.java:L19`).
- Indirect: CPU writes `VkDrawIndexedIndirectCommand` (32 B stride) into a HOST_MEM `IndirectBuffer(1_000_000)` per frame-in-flight (`WorldRenderer.allocateIndirectBuffers` L146-L153), then one `vkCmdDrawIndexedIndirect(drawCount)` **per area per layer** (`DrawBuffers.java:buildDrawBatchesIndirect` ~L222-L328). `baseInstance = inAreaIndex` indexes the per-section data. CPU backface culling per section builds a 6-bit facing mask (`getMask`) and **coalesces adjacent visible facings into a single draw** (merging index ranges because facings are stored contiguously) - drawCount shrinks.
- Early-Z fragment shader variant `terrain_earlyZ` (`layout(early_fragment_tests) in;` `shaders/basic/terrain_earlyZ/terrain_earlyZ.fsh:L3`) used for opaque layers (`PipelineManager.getTerrainIndirectShader` returns it, `render/shader/PipelineManager.java:L100-L102`, config `PipelineConfigs.TERRAIN_EARLY_Z_CONFIG`). `uniqueOpaqueLayer` option merges solid+cutout into one layer (`Config.java:L21`; `WorldRenderer.java` allowedRenderTypes).
Build/upload:
- Mesher threads (`TaskDispatcher`, count = max((cores-1)/2,1) `TaskDispatcher.java:L35`), `BuildTask` -> `UploadBuffer`s (per facing byte buffers) -> main thread `uploadSections()` (`WorldRenderer.java:L~226-L245`) -> `DrawBuffers.upload` -> `UploadManager.recordUpload` batched into one transfer cmd buffer per frame submitted at frame start (`Renderer.submitUploads`).
- Translucent sorting: `SortTransparencyTask`, re-sort threshold on camera move (`sortTranslucentSections`), rewrites index buffer segments only.
Culling (`render/chunk/graph/SectionGraph.java`):
- CPU BFS visibility graph identical in spirit to vanilla/Sodium: `ResettableQueue`, per-section `directionChanges`, `sourceDirs`, `visibility` bitmask of face connectivity (initVisibility L~120), `CONFIG.advCulling` (default 2) limits direction changes (L~170 `maxDirectionsChanges`), `notInFrustum` uses per-area frustum result cached (`ChunkArea.inFrustum(frustumIndex)`) then per-section test only when area INTERSECTs (L~230-L240), custom `VFrustum`. Re-run only if camera moved/rotated >2deg or section changes (`WorldRenderer.java:L~200-L222`, `graphNeedsUpdate`). No GPU/occlusion-query culling (Verified: no vkCmdBeginQuery occlusion in terrain; Strongly inferred).
- `entityCulling` option, `backFaceCulling` option (CPU per-facing).
Metal transfer: (a) area-sized (512 sections) mega vertex buffers + free-list suballocator = identical to what a Metal terrain path wants (few large MTLBuffers, `setVertexBuffer` once per area); (b) 16-byte compressed vertex halves bandwidth vs 28-32 B vanilla, matters on Apple GPUs (bandwidth bound); (c) coalescing facing ranges reduces draw count; (d) with no multiDrawIndirect in Metal, use **ICB** (indirect command buffer) filled on CPU/GPU or one `drawIndexedPrimitives(instanceCount, baseVertex, baseInstance)` per merged range: note Metal supports `baseVertex` and `baseInstance` in direct draws, so VulkanMod's `baseInstance`=section-index trick works w/o indirect (Strongly inferred; vanilla 26.3 uses the same trick, see vanilla-renderpearl.md TL;DR 6); (e) keep CPU BFS culling (cheap) and optionally GPU-driven culling via ICB compute later; (f) TBDR: early-Z shader variant is moot on Apple GPUs (HSR/tile deferred already removes overdraw for opaque), but `discard`/alpha-test layers defeat HSR: render opaque (no discard) first, then cutout, which VulkanMod's layer ordering already does.

### B5. Shaders and pipelines
- Runtime GLSL -> SPIR-V with **shaderc** (`vulkan/shader/SpirvCompiler.java:L25-L65`): target `vulkan_1_2`, `auto_bind_uniforms`, `auto_map_locations`, include callbacks to `/assets/vulkanmod/shaders/include/`; `OPTIMIZATIONS=false` (L18; so SPIR-V is unoptimised), `DEBUG=true` (debug info on). No on-disk SPIR-V cache (comment TODO "dump Shader Compiled Binaries … allow easy caching", `SpirvCompiler.java` releaser) - Verified.
- Reflection via **spvc** (SPIRV-Cross C API, `SpirvShader.java`): extracts UBO sizes, samplers, stage inputs/outputs; `SpirvPipeline.java` builds descriptor layouts from reflected data / or from `PipelineConfig` (Java builder with explicit UBs `PipelineConfigs.java:L9-L50` for terrain) - i.e. custom shaders are declared in Java (`PipelineConfig`) AND JSON (`terrain_earlyZ.json`) rather than purely reflected.
- Pipelines: `GraphicsPipeline` keeps `Object2LongMap<PipelineState> graphicsPipelines` (lazy creation per state combination: blend/depth/cull/topology/logic-op/renderpass(attachment formats) packed as ints `PipelineState.java`), `vkCreateGraphicsPipelines` with a single process-wide `VkPipelineCache` created EMPTY (`vulkan/shader/Pipeline.java:L32-L48`, no initial data, never serialised -> Verified: `grep -rn vkGetPipelineCacheData src` returns nothing) => every launch recompiles all pipelines (stutter source; fix = persist cache). Pipeline key includes the render pass (attachment formats) when not dynamic (`GraphicsPipeline.java:L47-L48,L197-L207`).
- **Attachment model (VulkanMod's answer to the key problem):** `vulkan/framebuffer/RenderPass` has `AttachmentInfo(format, loadOp, storeOp, finalLayout)` for exactly 1 colour + optional depth. With `DYNAMIC_RENDERING=true` (default) `beginDynamicRendering` is used and pipelines are created with `VkPipelineRenderingCreateInfo`-style formats (Strongly inferred; not read) so passes are cheap to create. Legacy path caches `VkFramebuffer` per render pass in `Framebuffer.renderpassToFramebufferMap` (`Framebuffer.java:L~134`). Viewport flips Y with negative height (`Framebuffer.viewport` `Framebuffer.java:L137-L145`) - differs from 26.3 vanilla Vulkan (no flip; flips in final blit, see vanilla-renderpearl.md TL;DR 5).
- Layout transitions are tracked in `VulkanImage` (`transitionImageLayout`, `readOnlyLayout` called on descriptor bind `DescriptorSets.java:L115,L203`, `DefaultMainPass.java:L91,L107,L150`) and barriers inserted lazily at bind time. Heavier than vanilla's global memory barrier approach; irrelevant on Metal (hazard tracking by driver unless `MTLResourceHazardTrackingModeUntracked` + manual fences).
- No compute shaders used in the renderer (`ComputeQueue` stub, `COMPUTE_SHADER` enum only; Verified by grep `vkCmdDispatch` = none).

### B6. Present / swapchain
- `vulkan/framebuffer/SwapChain.java`: standard; recreated on `OUT_OF_DATE/SUBOPTIMAL` (`Renderer.java:L270-L283`), `renderFinishedSemaphores` per image (B2). Main target is a separate framebuffer (`DefaultMainPass`) blitted/transitioned to PRESENT (`DefaultMainPass.java:L107`).
- Metal: CAMetalLayer `nextDrawable` replaces acquire; `presentDrawable` replaces present; vsync via `displaySyncEnabled`; "MAILBOX"-like = triple buffering (`maximumDrawableCount=3`).

### B7. Vulkan-side performance techniques -> Metal/Apple GPU
1. Area-level mega-buffers with free-list suballocator + deferred free by frame: adopt (Metal heap or few large buffers; fewer `setVertexBuffer`). [B4]
2. 16 B compressed terrain vertex; position as int16 relative to area origin + per-area uniform offset (push constant -> Metal `setVertexBytes`). [B4]
3. Facing-sorted vertex ranges + CPU face-mask culling + draw merging. [B4]
4. `baseInstance`/draw-id as section index into a UBO of packed section offsets + fade times (3x7 bit offsets, 4096 B). Metal: `setVertexBuffer`+`[[base_instance]]`; Metal needs `base_instance` support on GPU family Apple4+ (Strongly inferred) - ok on all Apple Silicon.
5. Persist shader/pipeline compilation: VulkanMod does NOT (empty VkPipelineCache, no SPIR-V cache) - Metallium should use `MTLBinaryArchive` / on-disk MSL->metallib cache keyed by (SPIR-V hash, pipeline state) to avoid shader-compile stutter, a known VulkanMod pain point.
6. Frames in flight = 2 (config) with per-frame fence, per-frame indirect/uniform/staging; swapchain-image-count semaphores. Metal equivalent: triple-buffer inflight semaphore.
7. Transfer-queue async uploads batched into 1 cmd buffer per frame; on UMA skip.
8. Frustum test hierarchy: per-area cached result then per-section; re-run graph only on camera change thresholds (position or >2 deg rotation).
9. Mesher thread count (cores-1)/2; chunk builder pool (`ThreadBuilderPack`, `BuilderResources`).
10. Keep separate opaque/cutout/translucent layers; translucent back-to-front by area & section, re-sort at threshold.
11. VMA budget polling for memory display - Metal: `MTLDevice.currentAllocatedSize`/`recommendedMaxWorkingSetSize`.

## Cross-cutting recommendations for Metallium
1. Treat Sulkan as proof that custom `RenderPipeline`s + `ShaderSource`/GLSL supply + BindGroupLayout (UBO/sampler/texel buffer) + Sodium `compileProgram` swap are enough for large visual features on the vanilla SPI. For Iris: confirm the same pipeline-swap point (`ShaderChunkRenderer#compileProgram`) is where the Iris adapter intercepts Sodium terrain.
2. Our Metal backend must support: MRT up to 8 targets (vanilla already exposes), depth-only/colour-less passes (Sulkan emulates depth-only with a dummy R8 colour attachment; supporting zero-colour passes natively is better), sampling a depth attachment as `sampler2D` with NEAREST (shadow maps; manual compare), texel buffers (Sodium section time info), push-constant-like small data (<=128 B -> `setVertexBytes`), and cheap `submit()` + cheap pass begin/end (Sulkan creates a pass per entity shadow draw and 3+ submits per frame).
3. Avoid per-draw render passes on TBDR. Batch.
4. Pipeline cache: persistent (MTLBinaryArchive) - neither VulkanMod nor Sulkan has it.
5. Y-flip: VulkanMod flips with negative viewport height; vanilla 26.3 Vulkan does not (flip in final blit). Metal must follow the 26.3 convention (row 0 == clip y=-1) per vanilla-renderpearl.md.
6. Do not copy: Sulkan GPL-3.0 (viral); VulkanMod LGPL-3.0 (copy requires LGPL notices + compat); both: ideas only unless owner chooses licence.
